### 2.1 지식 맵 결함 — 원인 추정

`map/page.tsx`는 hover한 노드를 `focus` 상태로 들고, `useMemo`가 `focus`에 의존해 **노드·간선 객체 전체를 새로 만든다.** 그래서

1. **깜빡임** — 노드 사이 빈 공간을 지나면 `onNodeMouseLeave`가 `focus=null`로 바꿨다가 다음 노드에서 다시 설정한다. 그 사이 27개 노드 전부의 `opacity`가 1 → 0.3 → 1로 뒤집힌다. 노드 객체가 매번 새로 만들어져 React Flow가 매번 다시 측정·렌더하는 것도 가세한다.
2. **클릭 무반응** — `onNodeClick`은 있지만, 마우스를 누르는 사이 hover 변화로 노드가 다시 그려지면서 클릭이 유실되는 것으로 보인다. 클릭해도 무엇이 열리는지(상세로 이동한다는 단서) 화면에 없다.

L11 착수 시 브라우저에서 먼저 재현해 원인을 확정합니다(추정이 틀리면 고칠 곳이 달라집니다).

## 3. 이 계획이 지키는 입장

2차 기획의 네 원칙(엔진이 진실, 엔진이 표현 못 하는 현상은 랩으로 만들지 않음, 정답표 없음, 읽음 ≠ 숙련)을 그대로 지키고, 이번 요청에 맞춰 세 가지를 더합니다.

1. **화면에 나오는 숫자는 엔진이 계산한다.** 설계 가이드가 "풀을 80으로 늘리면 P95가 X ms로 내려간다"고 말할 때 X는 콘텐츠에 적지 않습니다. 가이드 단계는 `DesignTraits` 덮어쓰기와 인시던트 여부만 저장하고, 페이지가 열릴 때 엔진이 before/after를 계산합니다. 엔진 수식이 바뀌어도 가이드가 조용히 틀리지 않습니다.
2. **서술의 방향은 테스트가 지킨다.** 가이드 본문이 "이 조치로 DB 읽기 부하가 줄어든다"고 쓰면, 그 단계에 `claims: [{metric: dbReadLoad, direction: DOWN}]`을 함께 저장하고 **CI 테스트가 엔진 결과와 대조**합니다. 이것은 학습자에게 보여 주는 정답표가 아니라 *콘텐츠 회귀 테스트*입니다(ADR-0047의 "정답표를 두지 않는다"는 사용자 예측의 채점 얘기이고, 이 테스트는 그 정신 — 엔진과 어긋난 콘텐츠를 막는다 — 의 연장입니다).
3. **그림은 두 종류만 쓴다.**
   - *정적 그림* — 콘텐츠(DB)에 **Mermaid 텍스트**로 저장해 기존 `MermaidDiagram` 컴포넌트로 렌더링합니다. 설계 답안이 이미 Mermaid로 직렬화되므로(ADR-0035~0037) 어휘가 같습니다. 이미지 파일은 쓰지 않습니다(다크 모드·수정·리뷰 비용).
   - *살아 있는 그림* — 엔진 `SystemState`에서 파생하는 React Flow 시스템 다이어그램. 컴포넌트 색 = 사용률, 간선 굵기 = 트래픽, 병목 표시. 설계 캔버스(ADR-0037)와 같은 노드 종류를 씁니다.

### 하지 않는 것 (2차 기획의 안티골 유지)

동영상·강의 CMS, 외부 아티클 큐레이션, 퀴즈 문제은행·플래시카드, AI 튜터 자유 대화, 실제 기업 장애 사례 재구성 — 이유는 2차 기획 §3과 같습니다. 퍼즐·랩 결과는 이번에도 **숙련도에 반영하지 않습니다**(진행 기록은 브라우저 localStorage 편의 기능으로만).

## 4. 슬라이스

### L11 — 지식 맵 수리와 상호작용 *(작음, 가장 먼저)* — ✅ 완료 (Round E33, 2026-10-05)

> 원인 확정: hover가 React 상태라 노드·간선 전체를 재생성(노드 5개 훑기에 DOM 재삽입 118개). 덤으로 d3-zoom이 dblclick을 삼켜 더블클릭이 동작하지 않던 버그도 발견·수정. 상세는 PLAN.md Round E33.

사용자가 지금 겪는 결함이라 다른 슬라이스보다 먼저 합니다.

- **깜빡임 제거** — 노드·간선 객체는 맵 데이터가 바뀔 때만 만들고, hover 강조는 `className`/`style`만 바꾸는 가벼운 갱신으로(React Flow `setNodes` 부분 갱신 또는 CSS 변수). 노드를 떠날 때 즉시 해제하지 않고 짧게 지연(빈 공간 통과 시 원상 복귀 방지).
- **클릭 = 상세 패널** — 노드를 클릭하면 페이지 이동 대신 오른쪽 패널(모바일은 하단 시트)이 열립니다: 요약, 내 숙련 상태와 근거, 선행 개념 → 이 개념 → 후속 개념, 관련 랩·Build·Drill 바로가기, "개념 읽기" 버튼. 더블클릭·Enter는 상세로 이동.
- **경로 보기** — 선택한 개념까지의 선행 사슬을 강조("이걸 이해하려면 먼저 이것들").
- **필터·검색** — 카테고리, 숙련 상태(약점만 보기), 이름 검색. 키보드 탐색(Tab/화살표).
- **허브 문구** — `/learning` 허브와 맵 설명이 "25개 개념", "인시던트 7개"로 굳어 있다(지금은 27개·8개). 개수를 데이터에서 읽게 고친다.
- **완료 기준**: hover로 화면 전체 opacity가 바뀌지 않음(브라우저에서 노드 사이를 오가며 확인), 클릭 → 패널, 패널에서 상세·랩 이동, 375px 폭에서 하단 시트, 다크 모드.

### L12 — 시각 자료 기반 *(L13·L14·L15가 쓰는 공용 부품)*

- **콘텐츠 블록 모델** — 개념·장애 패턴·가이드가 공통으로 쓰는 블록 배열(JSONB): `text`(마크다운 일부), `diagram`(Mermaid + 캡션 + 대체 텍스트), `steps`(번호 붙은 메커니즘 단계), `numbers`(엔진 계산 결과를 넣을 자리 — §3-1), `callout`(주의/트레이드오프), `compare`(Before/After 두 그림 나란히).
- **`SystemDiagram` 컴포넌트** — 도메인별 토폴로지(Client → API → Cache/DB/Queue/외부 PG…)를 `SystemState`로 색칠. 토폴로지는 시뮬레이션 쪽 `SystemTopologyService.TOPOLOGY_FIELDS`와 설계 캔버스의 노드 종류를 그대로 씁니다(새 어휘를 만들지 않음). L14·L15·L16이 같은 컴포넌트를 씁니다.
- **Mermaid 테마** — 앱 테마/다크 모드 토큰에 맞춤(현재 컴포넌트의 테마 처리 확인 후 보강).
- **완료 기준**: 블록 렌더러 단위 렌더 확인(각 블록 1개씩 든 샘플 개념), `SystemDiagram`이 8개 도메인의 평시/인시던트 상태를 구분해 그림.

### L13 — 개념·장애 패턴 상세화

- **개념 27개**에 블록을 더합니다. 개념마다 최소:
  1. *메커니즘 그림* — 문제 상황과 해결 후 구조를 `compare` 블록으로(예: Single-flight — 동시 miss 8개가 DB로 가는 그림 vs 한 번만 가는 그림).
  2. *단계 설명* — "왜 그렇게 하면 풀리는가"를 3~5단계로.
  3. *숫자로 보기* — 관련 랩이 있으면 그 랩의 손잡이 하나를 바꾼 before/after를 엔진이 계산해 인라인 표시.
  4. *다른 개념과의 관계* — 기존 `related_concepts`를 문장으로 풀어 연결("Single-flight는 Cache Stampede를 막지만, TTL이 너무 짧으면 여전히 miss가 잦다 → 캐시 정책 분리").
- **장애 패턴 8개**에 *장애 타임라인*을 더합니다 — 엔진 `TelemetrySampler`로 그 인시던트가 시간에 따라 번지는 차트(퍼즐이 이미 쓰는 생성기)와, 어느 지표가 먼저 움직였는지 표시. 전파 경로 그림(어느 컴포넌트에서 시작해 어디로 번졌나). Bad Fix를 적용했을 때와 올바른 완화를 적용했을 때의 회복 곡선 비교(`TimedAction`으로 계산).
- **작성 순서**: 카테고리 하나(캐싱·데이터 접근 4개)로 파일럿 → 검토 → 나머지 카테고리. 개념 하나에 그림 1~2개, 단계 3~5개가 목표치(분량 상한을 둬서 "읽는 데 3분 이내"는 유지).
- **완료 기준**: 27개 개념 모두 메커니즘 그림 1개 이상, `LearningConceptCatalogTest`에 "모든 개념에 diagram 블록이 있다"·"Mermaid 문법 파싱 성공"(서버 쪽은 형식만, 렌더 오류는 브라우저 확인) 추가, 장애 패턴 8개 타임라인.

### L14 — 도메인 설계 가이드 상세 페이지 *(가장 큼)*

`/learning/guides/[domain]` — 8개 도메인(선착순 쿠폰, 알림 이벤트, 대규모 상품 조회, 주문/결제, 예약, 배치/정산, 실시간 추천 API, 카나리 배포).

**페이지 구성**

1. **요구사항과 숫자** — 이 서비스가 감당해야 하는 규모를 어림(관련 Capacity Lab 연결, 없으면 새로 만든다 — L15).
2. **기본 아키텍처** — Mermaid 그림 + 요청 흐름 설명 + 저장소·캐시·큐 선택 이유.
3. **시나리오 체인** *(핵심)* — 3~5개 단계가 이어지는 이야기. 각 단계는 같은 틀을 따릅니다.

   | 틀 | 내용 | 데이터 |
   |---|---|---|
   | 상황 | "트래픽이 20배, 그중 상위 10개 상품에 몰린다" | 인시던트 여부·트래픽 배율 |
   | 신호 | 무엇이 먼저 나빠지는가 — 엔진이 계산한 지표 + `SystemDiagram`의 빨간 컴포넌트 | 엔진 계산 |
   | 진단 | 왜 그런가, 어떤 개념인가 | 개념 링크 |
   | 조치 | **값 조정**(예: `cacheTtlSeconds` 10 → 60, 의미와 안전 범위) 또는 **설계 변경**(예: Single-flight 도입, 캐시 정책 분리) | `DesignTraits` 덮어쓰기 |
   | 결과 | before/after 수치와 그림 — 무엇이 좋아졌고 **무엇이 대가로 나빠졌나** | 엔진 계산 + `claims`(§3-2) |
   | 다음 | 남은 문제가 다음 단계의 상황이 된다(꼬리설계처럼) | 다음 단계 |

   각 단계 끝에 "이 단계를 직접 해 보기"(그 상태로 프리셋된 랩), "이 장애를 지표로 맞혀 보기"(그 도메인 퍼즐), "이 메커니즘을 구현하기"(Build), "실전으로"(Drill) 링크.
4. **체크리스트** — 기존 `DESIGN_GUIDANCE_BY_DOMAIN` 항목을 앵커로 두고 각 항목이 본문의 어느 단계에서 다뤄졌는지 연결. Design 세션 안의 안내도 같은 항목에서 해당 가이드 단계로 링크합니다(출처를 DB로 옮기고 프론트 상수는 제거 — ADR-0039와 같은 이동).
5. **흔한 실수** — 장애 패턴의 Bad Fixes 중 이 도메인 것.

**예시 — 대규모 상품 조회 (파일럿 도메인)**

```
1. 평시: API → Redis(TTL 10s) → DB primary. 가격·재고·리뷰를 한 키로 캐시.
2. 트래픽 20배 + hot key → hit ratio 급락, DB 읽기 사용률 급등 (신호)
   → Cache Stampede (진단) → Single-flight 도입 (설계 변경) → DB 읽기 ↓ (결과)
3. 그래도 TTL 10s가 짧아 miss가 잦다 → TTL을 일괄로 늘리면 가격이 stale해진다 (대가)
   → 캐시 정책 분리: 가격은 짧게, 리뷰는 길게 (설계 변경) → hit ratio ↑
4. 남은 읽기 부하 → read replica 2대 (값 조정) → DB 읽기 ↓, 대신 복제 지연이라는 새 위험
   → Hot Key 분산·Consistent Hashing으로 이어짐 (다른 개념 연결)
```

**데이터** — 새 테이블 `design_guides`(domain PK, 블록 JSONB) + 단계 배열(각 단계: 블록, `traits` 덮어쓰기, `incident`, `claims`, 링크). 시드는 마이그레이션(ADR-0002). 조회 API는 단계별로 엔진을 돌려 before/after `SystemState`를 함께 내려줍니다(엔진 호출은 마이크로초 단위라 페이지당 수십 번도 부담 없음 — 2차 기획 L5와 같은 근거).

**작성 순서**: 상품 조회(엔진 손잡이가 가장 풍부) 1개를 끝까지 만들어 사용자 검토 → 형식 확정 → 나머지 7개.

**완료 기준**: 8개 가이드, 가이드마다 그림 2개 이상·시나리오 단계 3개 이상, `DesignGuideClaimsTest`(모든 단계의 claims가 엔진 결과와 일치, 모든 traits 키가 그 도메인에서 실제로 쓰이는 값인지), 개념·랩·퍼즐·Build·Drill 링크가 실제로 존재하는지 검사(개념→Build slug 검사와 같은 방식), 375px 레이아웃·다크 모드 브라우저 확인.

### L15 — 랩 고도화

기존 Engine Lab 8개·Capacity Lab 3개에 기능을 더하고, 랩이 없는 개념을 메웁니다.

- **살아 있는 그림** — 손잡이를 바꾸면 `SystemDiagram`이 즉시 다시 칠해진다(병목이 옮겨 가는 것이 보인다 — "DB가 빨갛던 게 풀을 늘리니 외부 API가 빨개짐").
- **시간 축 재생** — `TelemetrySampler`로 "장애 시작 → 내가 고른 조치를 t초에 적용 → 회복"을 차트로 재생. 조치를 늦게 하면 적체가 얼마나 쌓이는지 보인다.
- **스윕(최적점 찾기)** — 손잡이 하나를 범위 전체로 돌려 지표 곡선을 그린다. 청크 크기의 U자, 풀 크기의 꺾이는 점, 레플리카 수의 수확 체감.
- **비교 모드** — 설정 A·B를 나란히(그림 두 개 + 지표 차이).
- **목표 과제** — "P95 300ms 이하, 풀은 80 이하로" 같은 목표를 달성하는지 판정(목표의 성립 가능성은 테스트로 검증 — 엔진으로 풀리는 목표만 둔다). 랩마다 2~3개.
- **Capacity Lab** — 자릿수 막대(로그 스케일)로 "내 답 vs 계산값" 시각화, 문제 추가(가이드 §1이 쓰는 도메인별 문제: 쿠폰 이벤트, 알림 발송량, 결제 TPS 등).
- **커버리지** — 개념 27개 × 랩 표를 만들고, 엔진이 표현하는 개념인데 랩이 없는 것을 추가(예: Circuit Breaker, Read Replica, DLQ, 커넥션 풀 크기). 엔진이 표현하지 못하는 개념은 L17 쪽이거나 랩을 두지 않음(2차 기획 원칙 2).
- **완료 기준**: 기존 8개 랩 모두 그림·재생·스윕 동작, 목표 과제의 성립성 테스트, 신규 랩 각각 도메인 테스트로 현상이 엔진에서 실제로 나는지 확인.

### L16 — 진단 퍼즐 고도화

한 화면·두 질문에서 **짧은 인시던트 대응**으로.

1. **관찰** — 지금처럼 지표 차트(점선 = 시작 시점).
2. **조사** *(신규)* — "로그 보기", "트레이스 보기", "컴포넌트별 지표 보기", "최근 변경 이력" 같은 조사 행동을 골라 증거를 더 연다. 조사마다 시간 예산을 쓴다(무작정 다 열면 점수가 깎이는 대신 맞히기 쉽다). 로그·트레이스는 Observability 쪽 생성기(`LogGenerator` 등)를 재사용합니다.
3. **진단** — 무슨 장애인가(지금처럼).
4. **조치** *(신규)* — 조치를 고르면 `TimedAction`으로 그 시점에 적용해 회복 곡선을 보여 준다. Bad Fix를 고르면 왜 안 되는지가 곡선으로 보인다(장애 패턴의 Bad Fixes와 같은 출처).
5. **해설** *(강화)* — 차트 위에 "이 지표가 먼저 움직였다" 주석, 전파 경로 그림, 관련 개념·가이드 단계·랩 링크.

부가 기능: 난이도(쉬움 = 조사 무제한·힌트, 어려움 = 지표 일부 숨김·시간 예산 적음), 도메인 고르기, 힌트 단계, 브라우저에 남는 연속 정답·도메인별 적중률(서버 기록 없음 — §3). 주간 What Would You Do?(C12)는 질문 형식을 바꾸지 않습니다(이미 답한 주의 퍼즐이 바뀌면 안 됨 — `PuzzleSet` 버전 규칙 유지).

**완료 기준**: 8개 도메인 모두 조사 증거·조치 곡선 생성, "올바른 조치는 회복, Bad Fix는 회복하지 않음"을 도메인별 테스트로 확인, 시드 결정성 유지(같은 seed = 같은 퍼즐).

### L17 — 메커니즘 시뮬레이터 *(2차 기획의 보류 항목 재개)*

2차 기획 §6은 "Visualize 위젯(Consistent Hashing 등)"을 **엔진 근거가 없는 프론트 전용 시뮬레이터**라 보류했습니다. 그 사이 상황이 바뀌었습니다 — 이제 같은 메커니즘들이 **Build 과제로 존재하고, 각 스테이지의 동작이 4개 언어 테스트로 고정돼 있습니다.** 위젯의 근거를 엔진 대신 Build 과제의 스펙에 두면 "채점과 무관한 별도 시뮬레이터"가 아니게 됩니다.

- **대상** — Build 10개 과제의 메커니즘: Rate Limiter(fixed window vs token bucket 경계 burst), Queue(visibility timeout·DLQ), Circuit Breaker(상태 기계), Retry/Backoff(지터 유무에 따른 재시도 몰림), Distributed Lock(lease 만료와 fencing token), Event Bus(fan-out·순서), Cache(LRU·TTL·stampede), Idempotency(처리 중 중복), Consistent Hashing(노드 추가 시 키 이동), Outbox(relay 장애·중복 전달).
- **원칙** — 위젯의 시나리오 수치는 그 Build 과제 스테이지의 수치와 같게("8개 스레드 동시 miss → 로더 1회"). 위젯마다 "이걸 직접 구현해 보기 → Build 스테이지 N" 링크. 순수 클라이언트 계산(결정론적), 서버 호출 없음.
- **파일럿** — 2차 기획의 재개 조건("가장 많이 틀리는 개념 1개로 파일럿")을 따라, 지금 데이터로 가장 많이 지적되는 개념의 메커니즘 하나로 먼저 만들고 반응을 본 뒤 확장합니다.
- **완료 기준**: 파일럿 위젯 1개 + 위젯 시나리오 수치가 Build 스테이지와 같은지 확인하는 테스트(위젯 시나리오를 데이터로 두고 Build 테스트와 같은 값을 쓰는지 대조).

## 7. ADR 후보

1. **설계 가이드의 수치는 저장하지 않고 엔진이 계산하며, 서술의 방향은 claims 테스트로 고정한다** (L14) — 콘텐츠와 엔진의 결합 방식이라 되돌리기 비용이 크고, "왜 숫자를 안 적었지?"가 놀라울 수 있습니다. 착수 시 작성.
2. **메커니즘 위젯은 엔진이 아니라 Build 과제 스펙을 근거로 둔다** (L17) — 2차 기획의 보류 결정(§6)을 뒤집는 것이라 기록이 필요합니다.
3. **도메인 설계 체크리스트의 출처를 프론트 상수에서 DB로 옮긴다** (L14) — ADR-0039와 같은 이동이라 별도 ADR 없이 ADR-0039를 근거로 인용할 가능성이 높습니다. 착수 시 판단.
