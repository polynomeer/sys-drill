# 시스템 디자인 워게임 기획서

## 1. 개요

본 문서는 백엔드 개발자를 위한 **시스템 디자인 워게임 서비스**의 기획안입니다.

이 서비스의 핵심은 사용자가 자연어 또는 아이콘 기반 인터페이스를 통해 시스템 아키텍처를 설계하고, Redis, Kafka, DB, Worker, Load Balancer, Cache, Queue 등의 구성요소를 실제 운영 환경처럼 조정하며, 트래픽 증가·장애·데이터 정합성 문제·성능 병목 상황을 시뮬레이션해보는 것입니다.

서비스의 목적은 단순히 시스템 디자인 면접의 정답을 외우게 하는 것이 아닙니다. 백엔드 개발자가 시스템 구성요소의 동작 원리, 설정값의 의미, 장애 전파 방식, 운영 대응 전략을 직접 실험하고 체득하게 하는 것입니다.

즉, 이 서비스는 다음과 같이 정의할 수 있습니다.

> 자연어와 드래그 앤 드롭으로 시스템을 설계하고, 실제 운영 시나리오를 시뮬레이션하며 Redis, Kafka, DB, 캐시, 큐, 워커, 장애 대응을 실전처럼 학습하는 백엔드 개발자용 시스템 설계 훈련 플랫폼입니다.

## 2. 문제 정의

백엔드 개발자는 실무에서 다양한 인프라와 미들웨어를 다룹니다. 대표적으로 Redis, Kafka, RDBMS, Message Queue, Load Balancer, CDN, Object Storage, Worker, Scheduler, Rate Limiter, Circuit Breaker 등이 있습니다.

그러나 많은 개발자가 이 구성요소들을 이론적으로는 알고 있어도, 실제로 어떤 상황에서 병목이 생기고 어떤 설정이 장애를 악화시키며 어떤 대응이 효과적인지는 체감하기 어렵습니다.

### 2.1 시스템 설계 학습의 추상성

시스템 디자인을 공부할 때 흔히 다음과 같은 표현을 접합니다.

- Redis를 캐시로 사용합니다.
- Kafka를 통해 비동기 처리를 합니다.
- DB Read Replica를 구성합니다.
- API 서버를 Scale-out합니다.
- Rate Limit을 적용합니다.
- Circuit Breaker를 둡니다.
- DLQ를 구성합니다.

하지만 이런 문장을 이해하는 것과 실제 운영 상황에서 판단하는 것은 다릅니다.

예를 들어 백엔드 개발자는 다음 질문에 답할 수 있어야 합니다.

- Redis TTL을 너무 짧게 잡으면 어떤 문제가 발생하는가?
- TTL을 너무 길게 잡으면 어떤 정합성 문제가 생기는가?
- Kafka partition 수보다 consumer 수가 많으면 어떤 일이 발생하는가?
- Kafka consumer lag이 증가하면 사용자 경험은 어떻게 악화되는가?
- DB connection pool이 고갈되면 어떤 지표가 먼저 변하는가?
- API 서버를 늘렸는데 왜 장애가 더 심해질 수 있는가?
- Read Replica를 추가했는데도 쓰기 병목이 해결되지 않는 이유는 무엇인가?
- Retry 정책이 왜 장애 복구가 아니라 장애 증폭으로 이어질 수 있는가?
- Cache Stampede는 실제로 어떤 지표로 관찰되는가?
- 외부 결제 API 장애가 내부 주문 시스템까지 어떻게 전파되는가?

기존 학습 방식은 이러한 질문을 텍스트로 설명하는 데 그치는 경우가 많습니다. 이 서비스는 사용자가 직접 설정값을 바꾸고, 시뮬레이션 결과를 보며, 왜 그런 현상이 발생하는지 체험하게 합니다.

### 2.2 실전 운영 경험의 부족

장애 대응 경험은 백엔드 개발자의 성장에 매우 중요합니다. 그러나 실제 운영 장애는 의도적으로 경험하기 어렵습니다. 회사에서 장애를 일부러 만들 수 없고, 주니어 개발자는 장애 대응의 핵심 의사결정 과정에 깊게 참여하기 어렵습니다.

결과적으로 많은 개발자는 다음과 같은 상황을 실전에서 처음 겪습니다.

- 알람이 울렸지만 어떤 지표를 먼저 봐야 할지 모릅니다.
- API latency가 증가했지만 원인이 API 서버인지 DB인지 Redis인지 Kafka인지 구분하지 못합니다.
- 서버를 늘리면 해결될 것 같지만 DB connection이 먼저 고갈됩니다.
- Retry를 늘렸지만 오히려 외부 API와 내부 시스템을 동시에 압박합니다.
- Kafka lag이 쌓였지만 partition, consumer, batch size, 외부 API rate limit 사이의 관계를 이해하지 못합니다.
- 캐시 장애가 발생했는데 DB까지 함께 죽는 이유를 뒤늦게 알게 됩니다.

이 서비스는 이런 상황을 안전한 학습 환경에서 반복적으로 경험하게 합니다.

### 2.3 기존 도구의 한계

기존의 학습 방식은 대략 다음 네 가지로 나눌 수 있습니다.

첫째, 책과 강의입니다. 개념 학습에는 좋지만, 직접 실험하고 결과를 관찰하기 어렵습니다.

둘째, 다이어그램 도구입니다. 아키텍처를 그릴 수는 있지만, 그 그림이 실제로 동작하지는 않습니다.

셋째, 클라우드 실습랩입니다. 실제 환경을 다룰 수 있지만, 초보자에게 진입 장벽이 높고 비용이 발생하며, 시나리오 기반 학습 구조가 약할 수 있습니다.

넷째, 시스템 디자인 면접 문제 풀이입니다. 설계 설명 능력을 기르는 데는 좋지만, 운영 중 장애가 어떻게 발생하고 지표가 어떻게 변하는지는 체감하기 어렵습니다.

따라서 필요한 것은 단순한 강의도, 단순한 다이어그램 도구도, 단순한 클라우드 실습도 아닙니다. 필요한 것은 **동작하는 아키텍처 모델 위에서 실험하고, 장애를 경험하고, 대응하며 학습하는 시뮬레이션 기반 훈련 환경**입니다.

## 3. 서비스 목적

이 서비스의 목적은 백엔드 개발자가 시스템 설계를 머리로만 이해하는 것이 아니라, 실제 운영하듯 실험하면서 이해하도록 만드는 것입니다.

### 3.1 핵심 학습 목표

사용자는 서비스를 통해 다음을 학습합니다.

- 시스템 구성요소 간 의존 관계
- 트래픽 증가 시 병목이 발생하는 위치
- Redis 캐시 정책의 효과와 위험
- Kafka partition, consumer, lag의 관계
- DB connection pool, index, lock, replication lag의 영향
- API 서버 scale-out의 한계
- 비동기 처리와 eventual consistency의 trade-off
- 장애 전파 방식
- Timeout, Retry, Circuit Breaker, Rate Limit의 역할
- 임시 대응과 근본 해결의 차이
- 운영 지표를 기반으로 원인을 추론하는 방법
- 사후 분석 리포트를 작성하는 방법

### 3.2 제품이 제공해야 하는 경험

사용자가 반드시 체감해야 하는 경험은 다음과 같습니다.

> “Redis TTL 하나를 바꿨을 뿐인데 DB 부하가 이렇게 달라지는구나.”

> “API 서버를 늘리는 것이 항상 답은 아니구나.”

> “Kafka consumer 수를 늘렸는데 partition 수가 부족하면 효과가 없구나.”

> “Retry를 무작정 늘리면 장애가 복구되는 것이 아니라 증폭될 수 있구나.”

> “캐시는 DB를 보호하지만, 캐시가 무너지면 DB 장애를 유발할 수 있구나.”

> “Read Replica는 읽기 부하에는 도움이 되지만 쓰기 병목을 해결하지는 못하는구나.”

> “장애는 하나의 컴포넌트에서 끝나지 않고 연결된 시스템 전체로 전파되는구나.”

이러한 체감이 제품의 핵심 가치입니다.

- 시스템 디자인 면접을 준비하는 개발자

- 장애 대응 경험이 부족한 백엔드 개발자

- 개발자 평가 및 성장 추적

## 5. 제품 컨셉

### 5.1 한 줄 컨셉

**시스템 디자인을 직접 플레이하며 배우는 백엔드 개발자용 워게임 플랫폼**입니다.

### 5.2 핵심 사용 방식

사용자는 다음 두 가지 방식으로 시스템을 설계할 수 있습니다.

첫째, 자연어 입력 방식입니다.

예를 들어 사용자가 다음과 같이 입력합니다.

> “쇼핑몰 주문 시스템을 만들고 싶습니다. 사용자는 상품을 조회하고, 주문하고, 결제하고, 주문 완료 알림을 받아야 합니다. 평상시에는 1,000 RPS이고 이벤트 기간에는 15,000 RPS까지 증가합니다.”

그러면 서비스는 기본 아키텍처 초안을 생성합니다.

```text
Client
  ↓
Load Balancer
  ↓
API Server
  ├── Redis Cache
  ├── PostgreSQL
  └── Kafka
        ↓
      Notification Worker
```

둘째, 아이콘 기반 인터페이스입니다.

사용자는 화면에서 직접 다음 구성요소를 배치하고 연결합니다.

```text
Client → Load Balancer → API Server → PostgreSQL
                             ├→ Redis
                             └→ Kafka → Worker
```

이때 각 아이콘은 단순한 그림이 아닙니다. 각 구성요소는 시뮬레이션 가능한 속성을 가진 노드입니다.

## 6. 핵심 기능

### 6.1 자연어 기반 시스템 설계

사용자는 복잡한 다이어그램 도구를 처음부터 익히지 않아도 됩니다. 자연어로 원하는 서비스를 설명하면 AI가 초기 아키텍처를 생성합니다.

예시 입력은 다음과 같습니다.

> “초당 5천 요청을 처리하는 URL Shortener를 설계해줘. Redis 캐시와 PostgreSQL을 쓰고 싶어.”

생성 결과는 다음과 같습니다.

- API Server
- Load Balancer
- Redis Cache
- PostgreSQL
- Background Worker
- Analytics Queue
- 기본 트래픽 모델
- 예상 병목 지점
- 초기 권장 설정값
- 주의해야 할 장애 시나리오

이 기능의 목적은 완성된 정답을 제공하는 것이 아닙니다. 사용자가 실험할 수 있는 출발점을 빠르게 만들어주는 것입니다.

### 6.2 아이콘 기반 아키텍처 빌더

사용자는 드래그 앤 드롭으로 구성요소를 배치합니다.

대표 컴포넌트는 다음과 같습니다.

- Client
- Load Balancer
- API Server
- Redis
- Kafka
- PostgreSQL
- MySQL
- MongoDB
- Elasticsearch
- S3 또는 Object Storage
- CDN
- Worker
- Scheduler
- Message Queue
- Rate Limiter
- Circuit Breaker
- External API
- Monitoring
- Alerting

각 컴포넌트는 설정값을 가집니다.

Redis 노드 예시는 다음과 같습니다.

```yaml
type: redis
memory: 1GB
max_connections: 1000
ttl_default: 300s
eviction_policy: allkeys-lru
persistence: none
latency_ms: 1
replica_count: 1
failover_enabled: true
```

Kafka 노드 예시는 다음과 같습니다.

```yaml
type: kafka
brokers: 3
partitions: 12
replication_factor: 3
producer_ack: all
consumer_count: 4
retention: 7d
batch_size: 100
retry_policy: exponential_backoff
dlq_enabled: true
```

DB 노드 예시는 다음과 같습니다.

```yaml
type: postgresql
cpu: 4
memory: 16GB
max_connections: 300
read_replica: 1
indexing: partial
replication_lag_ms: 50
connection_pool_size: 50
```

API 서버 노드 예시는 다음과 같습니다.

```yaml
type: api_server
instances: 4
cpu_per_instance: 2
memory_per_instance: 4GB
thread_pool_size: 200
db_pool_size: 30
timeout_ms: 1000
retry_count: 1
```

이처럼 각 노드가 구체적인 설정값과 한계를 가지기 때문에, 사용자는 설정을 바꾸며 결과를 확인할 수 있습니다.

### 6.3 트래픽 시뮬레이션

서비스는 사용자가 만든 아키텍처에 트래픽을 주입합니다.

트래픽 모델은 다음과 같은 속성을 가질 수 있습니다.

```yaml
traffic:
  total_rps: 15000
  duration_minutes: 10
  read_ratio: 0.7
  write_ratio: 0.3
  ramp_up_seconds: 60
  endpoint_distribution:
    GET /products: 60%
    POST /orders: 20%
    POST /payments: 10%
    GET /orders/{id}: 10%
```

사용자는 평상시 트래픽, 이벤트 트래픽, 갑작스러운 스파이크, 특정 API 집중 호출, 외부 API 지연 등의 상황을 실험할 수 있습니다.

### 6.4 시나리오 기반 장애 주입

서비스는 특정 운영 상황을 시나리오로 부여합니다.

예시는 다음과 같습니다.

- 이벤트 시작으로 트래픽이 15배 증가합니다.
- Redis memory가 가득 차 eviction이 발생합니다.
- Redis primary가 다운됩니다.
- Kafka consumer lag이 급격히 증가합니다.
- DB connection pool이 고갈됩니다.
- 특정 쿼리가 인덱스를 타지 않아 DB CPU가 100%에 도달합니다.
- 외부 결제 API latency가 5초 이상으로 증가합니다.
- Worker가 poison message 때문에 계속 실패합니다.
- Read Replica lag이 커져 사용자에게 오래된 데이터가 보입니다.
- 배포 후 특정 API error rate가 급등합니다.
- Retry storm이 발생해 장애가 증폭됩니다.

사용자는 이 상황을 지표로 확인하고 대응해야 합니다.

### 6.5 실시간 관측 대시보드

사용자는 시뮬레이션 실행 중 다음 지표를 확인합니다.

- RPS
- Error Rate
- p50 latency
- p95 latency
- p99 latency
- CPU 사용률
- Memory 사용률
- DB connection count
- DB lock wait
- slow query count
- Redis hit ratio
- Redis memory usage
- Redis eviction count
- Kafka producer throughput
- Kafka consumer lag
- Queue depth
- Worker 처리량
- Retry count
- DLQ count
- 외부 API latency
- Circuit Breaker open count

이 대시보드는 단순 숫자 표시가 아니라 학습 도구입니다. 사용자는 장애 원인을 지표 기반으로 추론해야 합니다.

### 6.6 대응 액션 선택

사용자는 장애 상황에서 대응 액션을 선택합니다.

예를 들어 Redis 장애 상황에서는 다음 액션을 선택할 수 있습니다.

- Redis replica promotion
- Redis memory 증설
- TTL 조정
- eviction policy 변경
- cache warming 실행
- stale cache 허용
- hot key 분산
- DB rate limit 적용
- circuit breaker 적용
- cache aside 전략 개선

Kafka lag 상황에서는 다음 액션을 선택할 수 있습니다.

- consumer 수 증가
- partition 수 증가
- batch size 조정
- retry 정책 변경
- DLQ 도입
- worker scale-out
- 외부 API rate limit 대응
- idempotency key 적용

DB connection pool 고갈 상황에서는 다음 액션을 선택할 수 있습니다.

- connection pool 크기 조정
- API 서버 수와 pool 크기 재조정
- read replica 추가
- query timeout 설정
- DB pooler 도입
- slow query 개선
- index 추가
- API별 connection pool 분리

### 6.7 결과 평가 리포트

시뮬레이션이 끝나면 서비스는 결과를 평가합니다.

예시는 다음과 같습니다.

```text
결과:
- p95 latency: 2,400ms → 380ms
- error rate: 12% → 1.5%
- DB CPU: 98% → 62%
- Redis hit ratio: 42% → 89%
- Kafka lag: 180,000 → 12,000

평가:
Redis TTL을 늘리고 cache warming을 적용한 것은 효과적이었습니다.
다만 Redis memory 증설만으로는 장기적인 해결이 어렵습니다.
인기 상품 hot key 분산과 stale cache 전략을 함께 고려해야 합니다.

주의:
API 서버 scale-out은 상품 조회 처리량을 늘리는 데 일부 도움이 되었지만,
DB connection 수를 증가시켜 장애를 악화시킬 위험이 있었습니다.
```

리포트는 다음을 포함해야 합니다.

- 어떤 지표가 악화되었는지
- 사용자가 어떤 대응을 했는지
- 대응 전후 지표가 어떻게 달라졌는지
- 대응의 장점과 한계
- 더 나은 대안
- 관련 개념 설명
- 다음 학습 미션 추천

## 8. 주요 시나리오

### 8.1 트래픽 급증 시나리오

상황은 다음과 같습니다.

> 블랙프라이데이 이벤트가 시작되었습니다. 평소보다 트래픽이 15배 증가했습니다.

관찰 지표는 다음과 같습니다.

- API latency 증가
- DB CPU 증가
- Redis hit ratio 변화
- Kafka lag 증가
- error rate 증가
- p95/p99 latency 증가

사용자 대응은 다음과 같습니다.

- API 서버 scale-out
- Redis cache 적용 범위 확대
- DB read replica 추가
- rate limit 적용
- queue 기반 비동기화
- Kafka partition 증가
- worker 수 증가

학습 포인트는 다음과 같습니다.

- scale-out만으로 해결되지 않는 병목 이해
- DB 병목과 캐시 효과 이해
- queue 도입의 장단점 이해
- latency와 consistency trade-off 이해

### 8.2 Redis 장애 시나리오

상황은 다음과 같습니다.

> Redis primary가 다운되었습니다. 캐시 미스가 급증하고 DB 부하가 폭증합니다.

관찰 지표는 다음과 같습니다.

- cache hit ratio 급락
- DB QPS 급증
- DB CPU 100%
- API timeout 증가
- 사용자 요청 실패 증가

사용자 대응은 다음과 같습니다.

- Redis replica promotion
- fallback strategy 적용
- cache warming
- stale cache 허용
- DB rate limit 적용
- circuit breaker 적용

학습 포인트는 다음과 같습니다.

- 캐시는 성능 최적화 수단이지만 장애 전파 지점이 될 수 있음
- cache aside 패턴의 취약점
- cache stampede
- graceful degradation
- fallback 설계

### 8.3 Kafka consumer lag 증가 시나리오

상황은 다음과 같습니다.

> 주문 이벤트는 계속 쌓이는데 알림 발송 worker가 따라가지 못합니다.

관찰 지표는 다음과 같습니다.

- Kafka lag 증가
- consumer 처리량 부족
- 알림 지연
- worker CPU 증가
- 외부 API latency 증가
- retry queue 증가

사용자 대응은 다음과 같습니다.

- consumer 수 증가
- partition 수 조정
- batch size 조정
- retry 정책 수정
- DLQ 도입
- 외부 API rate limit 대응
- idempotency key 적용

학습 포인트는 다음과 같습니다.

- Kafka partition과 consumer 병렬성의 관계
- consumer lag의 의미
- 재처리와 중복 처리 문제
- at-least-once 처리의 현실적인 위험
- DLQ의 필요성

### 8.4 DB connection pool 고갈 시나리오

상황은 다음과 같습니다.

> API 서버가 늘어나면서 DB connection이 한계에 도달했습니다.

관찰 지표는 다음과 같습니다.

- DB max connection 초과
- API timeout
- connection acquisition latency 증가
- DB CPU는 낮은데 요청은 실패
- 신규 API 서버 추가 후 장애 악화

사용자 대응은 다음과 같습니다.

- connection pool 크기 조정
- API 서버 수와 pool 크기 균형 조정
- connection pooler 도입
- timeout 설정 조정
- read replica 분산
- 쿼리 최적화

학습 포인트는 다음과 같습니다.

- 무작정 서버를 늘리면 DB 연결 수가 폭증할 수 있음
- CPU 사용률만 보면 병목을 놓칠 수 있음
- connection pool은 성능 설정이자 장애 방어선임

### 8.5 데이터 정합성 문제 시나리오

상황은 다음과 같습니다.

> 주문은 완료되었지만 결제 상태와 재고 상태가 서로 맞지 않습니다.

관찰 지표는 다음과 같습니다.

- 주문 상태 불일치
- 이벤트 중복 처리
- 일부 worker 실패
- retry 후 중복 차감
- 보상 트랜잭션 필요

사용자 대응은 다음과 같습니다.

- idempotency key 적용
- outbox pattern 도입
- saga pattern 적용
- transaction boundary 재설계
- reconciliation job 추가
- exactly-once에 대한 잘못된 기대 수정

학습 포인트는 다음과 같습니다.

- 분산 시스템에서 정합성은 자동으로 보장되지 않음
- 이벤트 기반 아키텍처의 장단점
- 중복 처리 방지
- eventual consistency
- 보상 트랜잭션

서비스는 자유 시뮬레이션만 제공하면 초보자가 길을 잃을 수 있습니다. 따라서 커리큘럼형 미션과 샌드박스형 실험을 함께 제공해야 합니다.

- Load Balancer
- API Server
- RDBMS
- Redis Cache
- Message Queue
- Worker
- CDN
- Object Storage

예시 미션은 다음과 같습니다.

- 캐시 없이 상품 조회 API 운영하기
- Redis를 붙이면 latency가 어떻게 바뀌는지 확인하기
- Queue 없이 이메일을 동기 발송하면 어떤 문제가 생기는지 확인하기

### 9.2 Level 2. 병목 이해

- DB bottleneck
- network bottleneck
- connection pool bottleneck

- hot key
- slow query

예시 미션은 다음과 같습니다.

- API 서버를 1대에서 10대로 늘려보기

- 인덱스 없는 쿼리가 트래픽 증가 시 어떻게 장애로 이어지는지 보기

### 9.3 Level 3. Redis 운영

목표는 Redis를 단순 캐시가 아니라 운영 대상 컴포넌트로 이해하는 것입니다.

학습 주제는 다음과 같습니다.

- cache aside
- write through
- write back
- TTL
- eviction policy
- hot key
- cache stampede
- stale cache
- Redis replication
- Redis failover

예시 미션은 다음과 같습니다.

- TTL을 너무 짧게 설정했을 때 DB 부하 관찰
- TTL을 너무 길게 설정했을 때 stale data 문제 관찰
- hot key로 Redis 단일 shard가 터지는 상황 대응
- Redis 장애 시 DB가 같이 죽는 상황 방어

### 9.4 Level 4. Kafka 운영

목표는 Kafka를 단순 메시지 큐가 아니라 파티션, consumer lag, 재처리, 중복 처리까지 포함해 학습하는 것입니다.

학습 주제는 다음과 같습니다.

- topic
- partition
- consumer group
- offset
- consumer lag
- replication factor
- producer ack
- retry
- DLQ
- idempotency
- ordering guarantee

예시 미션은 다음과 같습니다.

- worker가 느려져 lag이 쌓이는 상황
- 메시지 중복 처리로 포인트가 두 번 적립되는 상황
- DLQ 없이 poison message가 전체 처리를 막는 상황

### 9.5 Level 5. DB 확장과 정합성

목표는 DB를 백엔드 시스템의 핵심 병목이자 정합성 중심 컴포넌트로 이해하는 것입니다.

학습 주제는 다음과 같습니다.

- index
- transaction
- lock
- isolation level
- read replica
- replication lag
- sharding
- connection pool
- migration
- backup and recovery

예시 미션은 다음과 같습니다.

- 주문 생성 API에서 lock contention이 발생하는 상황
- 서버 scale-out 후 DB connection이 고갈되는 상황
- 샤딩 키를 잘못 잡아서 특정 shard에 트래픽이 몰리는 상황

### 9.6 Level 6. 장애 대응 워게임

목표는 실제 운영 장애처럼 문제를 탐지하고 대응하는 것입니다.

## 10. MVP 범위

처음부터 실제 Redis, Kafka, DB를 모두 실행하는 방식은 비용과 구현 난도가 높습니다. MVP에서는 **추상 시뮬레이션 엔진**을 기반으로 시작하는 것이 적합합니다.

### 10.1 MVP 핵심 기능

MVP는 다음 기능을 포함합니다.

- 자연어로 시스템 요구사항 입력
- 기본 아키텍처 자동 생성
- 드래그 앤 드롭 아키텍처 편집
- 제한된 컴포넌트 제공
  - Client
  - Load Balancer
  - API Server
  - Redis
  - PostgreSQL
  - Kafka
  - Worker
- 트래픽 시뮬레이션
- 장애 시나리오 주입
- 지표 대시보드
- 대응 액션 선택
- 결과 리포트 제공

### 10.2 첫 번째 MVP 미션

첫 번째 MVP 미션은 **쇼핑몰 이벤트 트래픽 워게임**이 적합합니다.

이유는 Redis, Kafka, DB, Worker, Load Balancer, API Server를 모두 자연스럽게 사용할 수 있기 때문입니다.

미션 요구사항은 다음과 같습니다.

```text
기능:
- 상품 조회
- 주문 생성
- 결제 요청
- 주문 완료 알림

트래픽:
- 평상시 1,000 RPS
- 이벤트 시 15,000 RPS

SLO:
- 상품 조회 p95 latency 200ms 이하
- 주문 생성 p95 latency 500ms 이하
- 주문 실패율 1% 이하
- 알림은 5분 이내 발송
```

기본 구성은 다음과 같습니다.

```text
Client
  ↓
Load Balancer
  ↓
API Server
  ├── Redis
  ├── PostgreSQL
  └── Kafka
        ↓
      Worker
```

첫 장애 시나리오는 다음과 같습니다.

```text
이벤트 시작 후 상품 조회 트래픽이 급증합니다.
Redis hit ratio가 낮아 DB read QPS가 폭증합니다.
PostgreSQL CPU가 95%에 도달하고 API latency가 급등합니다.
```

사용자가 선택할 수 있는 대응은 다음과 같습니다.

- Redis TTL 증가
- cache warming
- 인기 상품 pre-cache
- DB read replica 추가
- API 서버 scale-out
- rate limit 적용
- 상품 조회와 주문 생성 API 분리
- CDN 도입

평가 기준은 다음과 같습니다.

- p95 latency
- error rate
- DB CPU
- Redis hit ratio
- 비용
- 구조 복잡도
- 데이터 정합성 위험

## 11. 시뮬레이션 엔진 설계

MVP에서는 실제 인프라를 띄우기보다 교육 목적의 추상 시뮬레이션 엔진을 사용합니다.

### 11.1 시스템 모델

각 컴포넌트는 다음 값을 가집니다.

```typescript
type Component = {
  id: string;
  type: ComponentType;
  capacity: CapacityModel;
  latency: LatencyModel;
  failureModes: FailureMode[];
  config: Record<string, unknown>;
};
```

### 11.2 요청 흐름 모델

요청은 시스템 그래프를 따라 이동합니다.

```typescript
type RequestFlow = {
  endpoint: string;
  rps: number;
  readWriteRatio: {
    read: number;
    write: number;
  };
  path: string[];
};
```

예시는 다음과 같습니다.

```typescript
{
  endpoint: "GET /products/:id",
  rps: 10000,
  readWriteRatio: {
    read: 1,
    write: 0
  },
  path: ["lb", "api", "redis", "postgres"]
}
```

### 11.3 병목 계산

각 노드는 처리 가능한 capacity를 가집니다.

```text
utilization = incoming_load / max_capacity
```

utilization이 높아질수록 latency와 error rate가 증가합니다.

단순화된 기준은 다음과 같습니다.

```text
0~60%: 안정
60~80%: latency 증가
80~95%: p95/p99 급등
95% 이상: error 증가
100% 이상: timeout/drop 발생
```

이 방식은 실제 인프라를 완벽하게 재현하지는 않지만, 교육적으로 충분히 의미 있는 결과를 제공합니다.

### 11.4 이벤트 기반 시뮬레이션

시뮬레이션은 시간 단위로 진행됩니다.

예시는 다음과 같습니다.

```text
t=0s: 평상시 트래픽 1,000 RPS
t=60s: 이벤트 시작, 15,000 RPS까지 증가
t=120s: Redis hit ratio 하락
t=180s: DB CPU 95% 도달
t=210s: API p95 latency 2초 초과
t=240s: 사용자가 cache warming 실행
t=300s: Redis hit ratio 회복
t=360s: DB CPU 안정화
```

이 구조를 사용하면 사용자가 특정 시점에서 대응 액션을 선택하고 그 결과를 관찰할 수 있습니다.

## 12. AI 코치 기능

AI는 단순한 아키텍처 생성기가 아니라 훈련 코치 역할을 해야 합니다.

### 12.1 AI의 역할

AI는 다음 역할을 수행합니다.

- 자연어 요구사항 파싱
- 초기 아키텍처 생성
- 사용자 설계 리뷰
- 시뮬레이션 결과 해석
- 장애 원인 후보 제시
- 대응 액션의 장단점 설명
- 사후 리포트 작성
- 다음 학습 미션 추천

### 12.2 AI와 시뮬레이션 엔진의 역할 분리

중요한 원칙은 다음과 같습니다.

> AI는 설명을 담당하고, Simulation Engine은 계산을 담당합니다.

시뮬레이션 수치를 AI가 임의로 생성하면 신뢰성이 떨어집니다. 따라서 latency, error rate, throughput, lag, CPU, connection count 등의 수치는 Simulation Engine이 계산해야 합니다.

AI는 그 결과를 기반으로 원인, 대응, trade-off, 개선 방향을 설명해야 합니다.

### 12.3 AI 피드백 예시

```text
현재 설계에서는 Redis가 상품 조회 트래픽을 대부분 흡수하고 있습니다.
하지만 TTL이 30초로 짧아 이벤트 시작 후 cache miss가 반복적으로 발생합니다.

추천 대응:
1. 인기 상품 cache warming
2. TTL을 5분 이상으로 증가
3. stale cache 허용
4. 주문 생성 API와 상품 조회 API의 DB connection pool 분리

주의:
API 서버를 늘리는 것만으로는 DB 병목이 해결되지 않습니다.
오히려 DB connection 수가 증가해 장애가 악화될 수 있습니다.
```

## 15. 차별화 포인트

### 15.1 그림이 아니라 동작하는 아키텍처

일반적인 다이어그램 도구는 구조를 그릴 뿐입니다. 이 서비스에서는 각 노드가 성능 특성, 장애 확률, 용량 한계, 설정값을 가집니다.

따라서 사용자는 다음과 같은 실험을 할 수 있습니다.

```text
Redis memory를 512MB로 낮추면 어떻게 되는가?
Kafka partition을 3개에서 12개로 늘리면 lag이 줄어드는가?
DB max connection을 100으로 제한하면 어떤 API부터 실패하는가?
API timeout을 1초로 줄이면 error rate가 어떻게 변하는가?
Retry를 3회로 늘리면 외부 API 장애 시 어떤 일이 발생하는가?
```

### 15.2 정답보다 피드백 중심

시스템 설계에는 절대적인 정답이 없습니다. 따라서 서비스는 정답을 알려주는 방식보다 피드백을 제공하는 방식이어야 합니다.

예시는 다음과 같습니다.

- 이 설계는 현재 트래픽에는 충분합니다.
- 하지만 이벤트 트래픽에서는 DB가 병목이 됩니다.
- Redis TTL이 너무 짧아 cache miss가 많습니다.
- Kafka partition 수보다 consumer 수가 많아서 일부 consumer가 놀고 있습니다.
- retry 정책 때문에 외부 API 장애 시 retry storm이 발생합니다.
- read replica를 추가했지만 쓰기 병목은 해결되지 않았습니다.
- API 서버를 늘렸지만 DB connection 수가 증가해 장애 위험이 커졌습니다.

### 15.3 운영 감각 학습

이 서비스의 진짜 가치는 운영 감각입니다.

사용자는 다음을 직접 경험합니다.

- 장애는 한 컴포넌트에서 끝나지 않고 전파됩니다.
- 서버를 늘리는 것이 항상 해결책은 아닙니다.
- 캐시는 DB를 보호하지만 잘못 쓰면 장애를 증폭합니다.
- Queue는 피크를 흡수하지만 지연과 정합성 문제를 만듭니다.
- Retry는 안정성을 높일 수 있지만 잘못 쓰면 장애를 키웁니다.
- Timeout, Circuit Breaker, Rate Limit은 설계의 핵심입니다.
- 정합성 문제는 나중에 reconciliation job이나 보상 트랜잭션으로 다뤄야 할 수 있습니다.

### 15.4 개인 학습과 기업 교육 모두 가능

초기에는 개인 개발자를 대상으로 시작할 수 있습니다. 이후 기업 교육, 부트캠프, 개발팀 온보딩으로 확장할 수 있습니다.

개인 개발자에게는 시스템 디자인 학습 도구가 되고, 기업에게는 백엔드/SRE 역량 훈련 플랫폼이 됩니다.

## 19. 핵심 리스크와 대응

### 19.1 시뮬레이션 정확도 리스크

실제 시스템은 매우 복잡합니다. 추상 시뮬레이션이 너무 단순하면 신뢰성이 떨어질 수 있습니다.

대응 방향은 다음과 같습니다.

- 실제 인프라의 완벽한 재현을 목표로 하지 않습니다.
- 교육 목적의 인과관계와 trade-off를 명확히 보여주는 데 집중합니다.
- 시뮬레이션 모델의 전제와 한계를 명시합니다.
- 고급 모드에서는 실제 benchmark 기반 파라미터를 추가합니다.

### 19.2 콘텐츠 제작 비용 리스크

좋은 시나리오를 만들려면 많은 도메인 지식이 필요합니다.

대응 방향은 다음과 같습니다.

- 초기에는 쇼핑몰 주문 시스템 하나에 집중합니다.
- Redis, Kafka, DB 등 범용적인 장애 패턴부터 구현합니다.
- 커뮤니티가 시나리오를 공유할 수 있는 구조로 확장합니다.
- 기업용에서는 사내 장애 사례를 커스텀 시나리오로 변환하는 기능을 제공합니다.

### 19.3 단순 게임처럼 보일 리스크

너무 게임화하면 실무 학습 도구로서 신뢰성이 떨어질 수 있습니다.

대응 방향은 다음과 같습니다.

- 시각적 재미보다 운영 지표와 피드백의 품질을 우선합니다.
- 실제 백엔드 용어와 운영 지표를 사용합니다.
- 사후 리포트와 개념 설명을 강화합니다.
- 포트폴리오나 면접 준비에 활용 가능한 결과물을 제공합니다.

이 서비스는 다음과 같이 포지셔닝하는 것이 가장 적합합니다.

> 백엔드 개발자를 위한 실전형 시스템 디자인 시뮬레이터입니다.  
> 자연어와 드래그 앤 드롭으로 아키텍처를 만들고, Redis, Kafka, DB, Worker, Cache, Queue 같은 컴포넌트의 설정을 바꿔가며 트래픽 증가와 장애 상황을 실험할 수 있습니다.  
> 사용자는 단순히 정답 설계를 외우는 것이 아니라, 시스템이 왜 느려지고 어디서 터지고 어떻게 복구되는지를 직접 경험하면서 배웁니다.

## 21. 결론

이 제품은 기존의 장애 대응 훈련 플랫폼보다 진입 장벽이 낮고, 개인 개발자에게 바로 제공할 수 있으며, 이후 기업 교육 시장으로 확장하기 좋습니다.

가장 중요한 전략은 다음과 같습니다.

> 실제 인프라를 처음부터 띄우지 말고, 교육 목적의 추상 시뮬레이션 엔진으로 시작해야 합니다.

초기 제품의 본질은 정확한 클라우드 에뮬레이션이 아닙니다. 백엔드 개발자가 다음 관계를 몸으로 이해하게 만드는 것입니다.

```text
설계 선택
→ 설정값 변화
→ 트래픽 변화
→ 병목 발생
→ 장애 전파
→ 대응 액션
→ 지표 개선 또는 악화
```

이 흐름을 직관적이고 재미있게 만들면, 이 서비스는 단순한 시스템 디자인 학습 도구가 아니라 **시스템을 실제로 운영하듯 배우는 백엔드 워게임 플랫폼**이 될 수 있습니다.

초기 MVP는 **쇼핑몰 이벤트 트래픽 워게임** 하나에 집중하는 것이 좋습니다. 이 미션 안에서 Redis 캐시, DB 병목, Kafka lag, Worker scaling, Retry, DLQ, Rate Limit, Connection Pool, Circuit Breaker까지 자연스럽게 다룰 수 있기 때문입니다.

결국 이 서비스의 핵심 가치는 다음 한 문장으로 정리됩니다.

> 백엔드 개발자가 시스템 디자인과 운영 장애 대응을 머리로 외우는 것이 아니라, 직접 설계하고 터뜨리고 복구하면서 배우게 하는 서비스입니다.
