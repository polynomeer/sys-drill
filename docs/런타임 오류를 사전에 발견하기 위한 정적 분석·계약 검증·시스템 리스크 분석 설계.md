# 런타임 오류를 사전에 발견하기 위한 정적 분석·계약 검증·시스템 리스크 분석 설계

## 1. 개요

애플리케이션에서 발생하는 오류 중 상당수는 실제 운영 환경에서 요청을 처리하기 전에 코드, API 명세, 데이터 스키마, 설정, 인프라 구성 등을 분석하여 발견할 수 있습니다.

대표적인 예가 다음과 같은 **API Contract 불일치**입니다.

```text
OpenAPI Specification
        │
        ├── Backend Implementation
        │
        └── Frontend / Client Implementation
```

API 명세에서는 다음 응답을 정의했다고 가정합니다.

```json
{
  "id": 123,
  "name": "Kim"
}
```

그러나 실제 서버에서는 다음과 같이 반환할 수 있습니다.

```json
{
  "userId": "123",
  "nickname": "Kim"
}
```

이 경우 다음과 같은 문제가 존재합니다.

- `id` → `userId` 필드명 불일치
- `id: integer` → `userId: string` 타입 불일치
- `name` 필드 누락
- 정의되지 않은 `nickname` 필드 추가

클라이언트가 기존 API 규격을 기준으로 작성되어 있다면 이는 런타임 오류로 이어질 수 있습니다.

하지만 API 명세와 서버 코드, 클라이언트 코드를 함께 분석할 수 있다면 이러한 오류는 실제 서비스를 실행하기 전에도 상당 부분 발견할 수 있습니다.

이 문서에서는 이러한 문제를 해결하기 위한 기존 기술을 살펴보고, 이를 한 단계 확장하여 **SysDrill의 정적 시스템 분석 및 런타임 리스크 시뮬레이션 기능**으로 발전시키는 방향을 정리합니다.

---

# 2. 정적 분석으로 발견 가능한 런타임 오류

정적 분석은 단순한 코드 스타일 검사를 의미하지 않습니다.

충분한 컨텍스트를 확보한다면 다음과 같은 문제들을 실행 전에 발견하거나 위험도를 추론할 수 있습니다.

### 코드 수준

- NullPointerException 가능성
- resource leak
- 잘못된 타입 변환
- unreachable code
- 잘못된 exception handling
- thread safety 문제
- 일부 race condition
- lock 사용 오류
- SQL injection
- 보안 취약점

### API 수준

- API 명세와 Controller 불일치
- Request/Response DTO 불일치
- required/optional 필드 불일치
- nullable 정책 불일치
- enum 값 불일치
- HTTP status code 불일치
- 클라이언트가 존재하지 않는 필드를 사용하는 문제
- 서버에서 삭제한 필드를 클라이언트가 계속 사용하는 문제

### 데이터 수준

- DB schema와 ORM entity 불일치
- nullable constraint 불일치
- column length 불일치
- enum/schema migration 문제
- 잘못된 index 설계
- transaction boundary 문제

### 이벤트 시스템

Kafka 등을 사용한다면 다음도 분석 대상이 됩니다.

```text
Producer
   │
   ▼
Kafka Topic
   │
   ▼
Consumer
```

- Producer/Consumer schema 불일치
- event version incompatibility
- 필드 삭제로 인한 consumer 오류
- enum 추가에 대한 consumer 미대응
- serialization/deserialization 오류 가능성

### 인프라/운영 수준

코드 외에 Kubernetes, Terraform, Docker, application.yml 등의 정보를 결합하면 다음과 같은 분석으로 확장할 수 있습니다.

- timeout 불일치
- connection pool 부족
- retry 폭증 가능성
- health check 설정 오류
- resource limit 부족
- autoscaling 한계
- replica 부족
- SPOF
- cache 장애 시 DB 부하 집중 가능성

즉 분석 대상을 코드 하나가 아니라 **전체 시스템 모델**로 확장할수록 실제 런타임 장애와 가까운 문제를 발견할 수 있습니다.

# 3. 기존 접근법 ① API Contract 기반 검증

질문에서 제시한 사례와 가장 직접적으로 대응하는 기술입니다.

대표적으로 다음을 사용할 수 있습니다.

- OpenAPI
- Swagger
- OpenAPI Generator
- Spectral
- TypeSpec
- Protocol Buffers
- Buf
- GraphQL SDL
- GraphQL Inspector

핵심 구조는 다음과 같습니다.

```text
                 API Contract
                      │
           ┌──────────┴──────────┐
           ▼                     ▼
     Backend Server          Client
           │                     │
           └──────────┬──────────┘
                      ▼
                Contract Check
```

예를 들어 OpenAPI가 다음과 같다고 가정합니다.

```yaml
GET /users/{id}

response:
  id: integer
  name: string
```

서버가 다음 DTO를 반환한다면

```kotlin
data class UserResponse(
    val userId: String,
    val nickname: String
)
```

다음과 같은 Contract Violation을 검출할 수 있습니다.

```text
ERROR GET /users/{id}

Expected:
  id: integer
  name: string

Actual:
  userId: string
  nickname: string

Problems:
  Missing field: id
  Missing field: name
  Unexpected field: userId
  Unexpected field: nickname
  Type mismatch: id / userId
```

이를 CI에 포함시키면 문제가 운영에 배포되기 전에 빌드를 실패시킬 수 있습니다.

# 4. 기존 접근법 ② Consumer-Driven Contract Testing

API 제공자가 작성한 명세만 검사하는 것으로 충분하지 않은 경우도 있습니다.

실제 클라이언트가 어떤 API를 사용하는지가 더 중요할 수 있기 때문입니다.

대표적인 도구가 Pact입니다.

구조는 다음과 같습니다.

```text
Frontend / Consumer
        │
        │ 기대하는 API
        ▼
    Pact Contract
        │
        ▼
Backend / Provider
        │
        ▼
Provider Verification
```

예를 들어 Consumer가 다음을 기대한다고 가정합니다.

```text
GET /users/1

{
    id: number,
    name: string
}
```

Backend 개발자가 다음과 같이 변경합니다.

```json
{
    "id": 1,
    "full_name": "Kim"
}
```

서버 자체 테스트는 성공할 수 있습니다.

하지만 Consumer Contract 관점에서는

```text
name field missing
```

이므로 CI가 실패합니다.

특히 다음 환경에서 가치가 높습니다.

- 마이크로서비스
- 프론트엔드/백엔드 조직 분리
- 독립 배포
- 여러 서비스 간 API 호출
- 외부 API 제공
- 버전 호환성이 중요한 플랫폼

# 5. 기존 접근법 ③ 타입 기반 End-to-End 검증

더 강한 접근법은 API Contract에서 코드를 생성하거나 동일한 타입 시스템을 공유하는 것입니다.

대표적으로 다음이 있습니다.

- OpenAPI Generator
- Protocol Buffers
- gRPC
- GraphQL Code Generator
- tRPC
- Zod
- TypeSpec

예를 들어 다음 타입을 기준으로 서버와 클라이언트를 생성합니다.

```text
User
 ├─ id: Long
 ├─ name: String
 └─ status: UserStatus
```

그러면

```text
API Specification
       │
       ├── Kotlin DTO
       │
       └── TypeScript Type
```

와 같이 동일한 Contract에서 양쪽 코드가 생성됩니다.

이를 통해 API 불일치 자체가 발생하기 어려운 구조를 만들 수 있습니다.

# 6. 기존 접근법 ④ 일반적인 정적 프로그램 분석

API가 아니라 프로그램 자체의 런타임 위험을 분석하는 도구도 존재합니다.

대표적으로 다음과 같습니다.

- CodeQL
- Semgrep
- SonarQube
- Infer
- Snyk Code

예를 들어 다음 코드가 있다고 가정합니다.

```java
User user = findUser(id);

if (user != null) {
    log.info("found");
}

return user.getName();
```

정적 분석기는 control flow와 nullability를 분석하여

```text
Potential NullPointerException
```

을 발견할 수 있습니다.

더 발전된 분석기는 다음과 같은 기법을 사용합니다.

- AST 분석
- Control Flow Graph
- Data Flow Analysis
- Taint Analysis
- Interprocedural Analysis
- Symbolic Execution
- Abstract Interpretation

즉 소스 코드를 단순 텍스트가 아니라 프로그램의 구조와 데이터 흐름으로 변환하여 분석합니다.

# 7. 기존 정적 분석의 한계

그럼에도 운영 장애가 사라지지 않는 이유는 실제 시스템의 동작이 소스 코드만으로 결정되지 않기 때문입니다.

## 7.1 동적 동작

다음과 같은 코드는 정적 분석이 어려워집니다.

```javascript
obj[fieldName]
```

Reflection, dynamic proxy, runtime code generation 등도 분석 난도를 높입니다.

## 7.2 실제 데이터

운영에서는 예상하지 못한 데이터가 들어옵니다.

```text
null
malformed payload
oversized payload
unexpected enum
old schema data
extreme cardinality
skewed partition
```

## 7.3 분산 시스템

다음 문제는 단일 프로그램 분석만으로 충분히 설명하기 어렵습니다.

```text
Network Partition
Timeout
Retry
Circuit Breaker
Kafka Lag
Redis Failure
DB Saturation
Thread Pool Exhaustion
Connection Pool Exhaustion
```

## 7.4 환경 차이

실제 장애의 상당수는 코드가 아니라 다음과 같은 환경 차이에서 발생합니다.

```text
application.yml
Kubernetes
Terraform
AWS
Load Balancer
DNS
IAM
DB configuration
JVM configuration
```

따라서 **코드 정적 분석만으로 실제 운영 장애를 예측하는 데는 명확한 한계가 있습니다.**

# 8. 중요한 확장 방향: 시스템 전체를 정적으로 분석한다

여기에서 SysDrill과 연결할 수 있는 중요한 아이디어가 나옵니다.

기존 정적 분석기가

```text
Source Code
     ↓
Analyzer
     ↓
Bug
```

를 분석한다면 SysDrill은 분석 범위를 다음과 같이 확장할 수 있습니다.

```text
Git Repository
      │
      ├── Kotlin / Java
      ├── TypeScript
      ├── OpenAPI
      ├── SQL
      ├── application.yml
      ├── Docker
      ├── Kubernetes
      └── Terraform
             │
             ▼
       System Analyzer
             │
             ▼
       System Model
             │
       ┌─────┴─────┐
       ▼           ▼
Static Analysis   Simulation
       │           │
       └─────┬─────┘
             ▼
        Risk Report
```

즉 **코드를 분석하는 것이 아니라 시스템을 분석하는 것**입니다.

# 9. SysDrill의 System Model

분석을 위해서는 다양한 입력을 하나의 중간 표현으로 변환할 필요가 있습니다.

예를 들어 다음 시스템이 있다고 가정합니다.

```text
Client
  │
  ▼
API Gateway
  │
  ▼
Order Service
  │
  ├──── Redis
  │
  ├──── MySQL
  │
  └──── Kafka
          │
          ▼
      Payment Service
```

SysDrill 내부에서는 이를 다음과 같은 모델로 표현할 수 있습니다.

```text
Service
Dependency
API
Database
Cache
MessageBroker
ThreadPool
ConnectionPool
RetryPolicy
TimeoutPolicy
ScalingPolicy
ResourceLimit
```

그리고 관계를 그래프로 표현합니다.

```text
OrderService
   │
   ├─ CALLS → PaymentService
   ├─ READS → Redis
   ├─ WRITES → MySQL
   └─ PRODUCES → OrderCreated
```

이 **System Graph**가 분석과 시뮬레이션의 핵심 데이터가 됩니다.

# 10. API Contract Drift 분석

SysDrill의 첫 번째 현실적인 기능으로 만들기 좋은 영역입니다.

입력:

```text
OpenAPI
Backend Controller
Backend DTO
Frontend API Client
```

분석:

```text
OpenAPI
   │
   ├──── Controller
   ├──── DTO
   └──── Frontend Client
```

결과:

```text
GET /api/users/{id}

OpenAPI:
    id: integer
    name: string
    status: ACTIVE | INACTIVE

Backend:
    id: Long
    name: String
    status: String?

Frontend:
    id: number
    username: string
```

SysDrill:

```text
HIGH
Frontend expects `username`
but backend returns `name`.

MEDIUM
Backend `status` is nullable,
but OpenAPI declares it required.

MEDIUM
Backend accepts arbitrary String values,
while API contract restricts status to
ACTIVE | INACTIVE.
```

단순 Swagger validation보다 한 단계 높은 **Cross-Layer Static Analysis**가 됩니다.

# 11. Event Contract Drift 분석

Kafka 같은 이벤트 시스템에도 동일한 원리를 적용할 수 있습니다.

```text
Order Service
      │
      │ OrderCreated
      ▼
    Kafka
      │
      ├── Payment Service
      ├── Inventory Service
      └── Notification Service
```

Producer가 이벤트를 변경합니다.

기존:

```json
{
    "orderId": 123,
    "price": 10000
}
```

변경:

```json
{
    "orderId": 123,
    "amount": 10000
}
```

Payment Service가 여전히 `price`를 사용한다면 배포 이후 장애가 발생합니다.

SysDrill은 repository들을 분석하여

```text
Order Service
   produces
       OrderCreated v2
            │
            ├── Payment Service ❌
            ├── Inventory Service ✓
            └── Notification Service ✓
```

와 같이 영향 범위를 보여줄 수 있습니다.

# 12. Timeout Chain 분석

분산 시스템에서는 timeout configuration 자체가 장애를 만들 수 있습니다.

예를 들어

```text
Client
 │ timeout 3s
 ▼
API
 │ timeout 5s
 ▼
Payment
 │ timeout 10s
 ▼
External PG
```

구조라면 상위 요청이 이미 종료된 이후에도 하위 요청이 계속 실행될 수 있습니다.

SysDrill은 이를 분석하여

```text
Timeout hierarchy violation

Client         3s
API            5s
Payment       10s
External PG   15s

Potential:
- wasted work
- thread occupation
- connection pool exhaustion
```

과 같은 경고를 제공할 수 있습니다.

---

# 13. Retry Amplification 분석

다음 구조를 생각할 수 있습니다.

```text
Gateway retry 3
       │
       ▼
Order retry 3
       │
       ▼
Payment retry 3
```

최악의 경우 하나의 사용자 요청이 하위 시스템에 매우 많은 요청을 만들 수 있습니다.

SysDrill은 호출 그래프와 retry 설정을 분석하여

```text
Retry amplification detected

Gateway
  ×3

Order Service
  ×3

Payment Client
  ×3

Worst-case downstream amplification:
27 requests / original request
```

처럼 표시할 수 있습니다.

이것은 코드 린터보다는 **시스템 아키텍처 린터**에 가깝습니다.

# 14. Redis 장애 전파 분석

다음 시스템이 있다고 가정합니다.

```text
                Redis
               /     \
              /       \
             ▼         ▼
       Product API   Order API
             │
             ▼
           MySQL
```

평소:

```text
Redis hit rate = 95%
DB QPS = 1,000
```

Redis가 장애를 일으키면:

```text
Redis hit rate = 0%
        ↓
DB QPS = 20,000
```

으로 변할 수 있습니다.

코드 자체에는 오류가 없지만 시스템 설계에는 위험이 존재합니다.

SysDrill에서는

```text
Scenario:
Redis unavailable

Predicted impact:

Redis
  ↓ FAILURE
Product API
  ↓ cache bypass
MySQL
  ↓
QPS +1,900%

Expected:
DB saturation
connection pool exhaustion
request latency increase
```

와 같은 분석을 제공할 수 있습니다.

# 15. Kafka 장애 시나리오

다음과 같은 이벤트 시스템에서도 분석이 가능합니다.

```text
Order
  │
  ▼
Kafka
  │
  ├── Payment
  ├── Inventory
  └── Notification
```

분석 대상은 다음과 같습니다.

- partition 수
- consumer concurrency
- consumer processing time
- retry 정책
- DLQ
- producer idempotence
- consumer idempotency
- offset commit 방식
- transaction 설정

예를 들어 consumer 처리량이 producer 처리량보다 낮다면

```text
Producer
10,000 msg/s

Consumer
6,000 msg/s
```

SysDrill은

```text
Kafka Lag Risk

Incoming:   10,000 msg/s
Processing:  6,000 msg/s

Lag growth:
4,000 msg/s

Expected lag after 10 minutes:
2,400,000 messages
```

와 같은 결과를 제공할 수 있습니다.

# 16. IaC 분석

Terraform과 Kubernetes까지 입력에 포함하면 분석 범위가 더욱 넓어집니다.

예:

```yaml
replicas: 2

    cpu: 500m
```

```text
Replica
2

Estimated capacity
3,200 RPS

Capacity deficit
6,800 RPS
```

와 같은 위험 분석이 가능합니다.

# 17. 정적 분석에서 시뮬레이션으로

여기까지 확장하면 SysDrill의 기존 핵심 개념과 자연스럽게 연결됩니다.

SysDrill의 핵심은

> 시스템을 설계하고 끝나는 것이 아니라 실제 상황을 부여하여 설계가 어떻게 동작하는지를 경험하게 하는 것

입니다.

따라서 다음 흐름을 만들 수 있습니다.

```text
① Repository Import
        ↓
② Static Analysis
        ↓
③ System Model 생성
        ↓
④ Risk Detection
        ↓
⑤ Scenario Generation
        ↓
⑥ Simulation
        ↓
⑦ User 대응
        ↓
⑧ 결과 분석
```

예를 들어 정적 분석 결과 다음 위험이 발견됩니다.

```text
Redis SPOF
```

그러면 AI가 자동으로 워게임을 생성합니다.

```text
[Incident]

14:02

Redis latency
2ms → 800ms

14:03

API P99
120ms → 2.3s

14:04

DB connections
70 → 198 / 200
```

사용자는 대응합니다.

```text
Circuit Breaker 적용

Redis timeout
500ms → 50ms

DB pool
200 → 300
```

SysDrill은 변경 결과를 다시 시뮬레이션합니다.

이렇게 하면 **Static Analyzer와 System Design Wargame이 하나의 제품 경험으로 연결됩니다.**

가 되는 편이 훨씬 강합니다.

# 20. 핵심 개념: Architecture Linter

이 기능을 제품 관점에서 표현한다면 **Architecture Linter**라는 개념으로 정의할 수 있습니다.

일반적인 Linter가

```text
잘못된 코드
```

를 발견한다면 Architecture Linter는

```text
잘못된 시스템 관계
```

를 발견합니다.

예를 들어:

```text
[HIGH]
Payment API timeout > Gateway timeout

[CRITICAL]
Redis failure can increase DB traffic by ~18x

[HIGH]
OrderCreated schema incompatible with Payment consumer

[MEDIUM]
Kafka consumer throughput below expected peak producer throughput

[HIGH]
Retry amplification can generate 27 downstream requests

[MEDIUM]
Single Redis instance detected

[HIGH]
No idempotency protection detected for payment retry

[MEDIUM]
Kafka consumer has retry but no DLQ strategy detected
```

이러한 결과는 백엔드 개발자에게 코드 린트보다 훨씬 실무적인 학습 자료가 될 수 있습니다.

# 21. AI를 적용할 수 있는 영역

LLM은 정적 분석기를 완전히 대체하기보다는 기존 deterministic analyzer 위에 위치하는 것이 적합합니다.

권장 구조는 다음과 같습니다.

```text
Source
  ↓
Parser
  ↓
AST / Schema
  ↓
Static Analyzer
  ↓
System Graph
  ↓
Rule Engine
  ↓
Simulation Engine
  ↓
LLM Reasoning
  ↓
Explanation / Scenario / Feedback
```

정확하게 판정할 수 있는 문제는 Rule Engine이 담당합니다.

예:

```text
timeoutA < timeoutB
schema incompatible
required field missing
consumer throughput < producer throughput
```

LLM은 그 결과를 기반으로 다음을 담당합니다.

- 위험 설명
- 원인 추론
- 개선안 생성
- 장애 시나리오 생성
- 사용자 대응 평가
- 꼬리 질문 생성
- 시스템 설계 인터뷰 진행

이렇게 하면 LLM의 hallucination에 핵심 판정을 맡기지 않으면서 AI의 장점을 활용할 수 있습니다.

# 24. 최종 제품 비전

이 아이디어에서 가장 중요한 것은 단순한 정적 분석기를 만드는 것이 아닙니다.

기존 도구들은 각각 다음 질문에 답합니다.

```text
SonarQube
"이 코드에 문제가 있는가?"

Pact
"API 계약이 깨졌는가?"

Terraform Validator
"인프라 설정이 올바른가?"

Datadog
"현재 시스템에서 무슨 일이 일어나고 있는가?"
```

SysDrill이 궁극적으로 답해야 할 질문은 조금 다릅니다.

> **“이 시스템을 실제 운영하면 어떤 문제가 발생할 수 있는가?”**

그리고 그 다음 질문까지 이어져야 합니다.

> **“그 문제가 실제로 발생했다고 가정하면 어떻게 대응해야 하는가?”**

이를 제품 흐름으로 표현하면 다음과 같습니다.

```text
             ┌──────────────────┐
             │   Repository     │
             └────────┬─────────┘
                      │
                      ▼
             ┌──────────────────┐
             │ Static Analysis  │
             └────────┬─────────┘
                      │
                      ▼
             ┌──────────────────┐
             │   System Graph   │
             └────────┬─────────┘
                      │
             ┌────────┴────────┐
             ▼                 ▼
     Contract Analysis    Architecture Lint
             │                 │
             └────────┬────────┘
                      ▼
             ┌──────────────────┐
             │   Risk Model     │
             └────────┬─────────┘
                      │
                      ▼
             ┌──────────────────┐
             │    Simulator     │
             └────────┬─────────┘
                      │
                      ▼
             ┌──────────────────┐
             │ Incident Engine  │
             └────────┬─────────┘
                      │
                      ▼
             ┌──────────────────┐
             │   SysDrill       │
             │     Wargame      │
             └──────────────────┘
```

이렇게 정의하면 SysDrill의 기존 핵심 기능인 **시스템 설계, Redis/Kafka 등 구성 요소 학습, 트래픽·장애 대응 훈련**과 이번 아이디어인 **정적 분석과 사전 런타임 리스크 탐지**가 별개의 기능이 아니라 하나의 제품 흐름으로 연결됩니다.

핵심적인 제품 명제는 다음과 같이 정리할 수 있습니다.

> **SysDrill은 코드를 검사하는 정적 분석기를 넘어, 애플리케이션 코드·API 계약·데이터·메시징·캐시·인프라를 하나의 시스템 그래프로 이해하고, 실제 운영에서 발생할 수 있는 장애와 성능 문제를 사전에 분석·시뮬레이션하며, 개발자가 그 상황에 직접 대응하도록 훈련시키는 System Design & Reliability Simulator입니다.**

이 방향은 단순한 시스템 디자인 문제 풀이 서비스보다 기술적 진입장벽과 실무 활용도를 높일 수 있으며, 장기적으로 교육용 서비스에서 실제 개발팀이 사용하는 **Continuous Architecture Validation / Pre-production Reliability Analysis 플랫폼**으로 확장할 수 있는 기반이 됩니다.
