# The diagram canvas is a drawing input method that serializes to the same Mermaid text, not a second source of truth

An external UI/UX design brief (`SysDrill_UIUX_Design_Plan.docx`) called for a node-and-edge diagram canvas (Client/API Gateway/Service/DB/Cache/Queue/CDN, drag to place, drag to connect) in the System Design Drill screen. [0035](0035-diagrams-are-mermaid-text-embedded-in-the-existing-answer-not-a-new-field-or-editor.md) had explicitly chosen Mermaid text over exactly this kind of editor for v1, on the grounds that a drawing editor "would need custom node types, layout persistence, and a serialization format decision before it could produce anything gradeable." That ADR also named its own reconciliation path in advance: "a later phase can add it as a drawing *input method* that serializes to the same Mermaid text and inserts it into the same textarea, keeping the DSL as the one durable format in both v1 and any v2." This ADR is that later phase, not a reversal — the three costs 0035 flagged still had to be paid, and the choice below is how each was paid down to roughly the smallest slice that could still ship as "the canvas."

**Custom node types**: seven fixed kinds (Client/API Gateway/Service/DB/Cache/Queue/CDN) built with `@xyflow/react`, each mapped to a specific Mermaid shape (`([label])`, `[label]`, `[(label)]`, `{{label}}`). No generic/user-defined node type, no node configuration beyond a label text field — this is a palette, not a modeling tool.

**Layout persistence**: node positions and edges are persisted, but only as a per-browser-tab localStorage draft (`sysdrill:canvas:<sessionId>`, mirroring the existing `sysdrill:draft:<sessionId>` answer-text draft) — not a new backend field or schema. This is deliberately the same durability tier as the answer draft itself, which also only lives in localStorage until submission.

**Serialization format decision**: the canvas produces a `flowchart TD` Mermaid block on every change and splices it into the same free-text `answer` the textarea already edits, inside HTML-comment markers (`<!-- sysdrill-canvas:start/end -->`) so re-serialization can find and replace its own output without touching anything the user typed by hand elsewhere in the answer. `Session.submit`'s `rawText` is exactly what 0035 promised it would remain: the free-text answer, unchanged in shape, still the one thing sent to evaluation. The canvas is additive UI on top of it, not a parallel field.

A consequence worth being explicit about, since it is the one real gap this trade-off leaves: **the canvas cannot parse an existing Mermaid block back into nodes and edges.** If a user hand-edits the mermaid block in "텍스트" mode, then switches to "캔버스" mode, the canvas shows its own last-known localStorage graph, not the hand-edited text — and further canvas edits will overwrite that hand-edited block on the next change. Building a Mermaid parser to close this gap was the exact cost 0035 was avoiding when it picked a DSL over an editor in the first place; accepting one-directional (canvas → text) sync for now, with "텍스트" mode kept purely as a manual-editing fallback rather than something meant to interoperate bidirectionally with the canvas, is what keeps this within "one small component" territory rather than reopening 0035's original trade-off.
