# Architecture diagrams are Mermaid text embedded in the existing free-text answer, not a new field or a drawing editor

The product had no way to visualize a system's architecture anywhere — the Design Workspace was (and mostly still is) a plain `<textarea>`, and the Architecture Linter only listed findings as text. PRD.md's MVP scope had intentionally excluded a "freeform architecture diagram editor," and ARCHITECTURE.md's tech-stack table left React Flow as an unresolved "review later" candidate for the design workspace. Both calls were made at Phase 1, long before Phase 5/6 shipped; revisiting the question now meant choosing a concrete direction rather than leaving it open indefinitely.

We picked a text DSL (Mermaid) over a mouse-driven node/edge editor for v1. A DSL costs one small rendering component and zero backend or schema changes: a user's diagram is just a ` ```mermaid ` fenced block inside the same free-text answer they already submit, so `Session.submit`'s `rawText` is untouched byte-for-byte and the LLM/rule evaluators need no changes. A drawing editor (React Flow) would need custom node types, layout persistence, and a serialization format decision before it could produce anything gradeable — real cost for a first slice whose only job is proving the visualization is wanted at all. This does not contradict PRD.md's original exclusion: what was ruled out was a freeform *mouse* editor, and Mermaid text is not one. It also doesn't abandon ARCHITECTURE.md's React Flow candidate — a later phase can add it as a drawing *input method* that serializes to the same Mermaid text and inserts it into the same textarea, keeping the DSL as the one durable format in both v1 and any v2.

Architecture Linter's diagram is generated server-side, deterministically, from the already-parsed `OpenAPI` object (`ArchitectureDiagramGenerator`, same traversal as `ArchitectureRiskScanner`) — no LLM, nothing new persisted, consistent with [0034](0034-architecture-linter-v1-is-openapi-only-no-retention-and-private-by-default.md)'s "parse, scan, discard" rule. `mermaid` is the frontend's first runtime dependency beyond next/react/tailwind; that alone would not normally warrant an ADR, but the trade-off it resolves (DSL vs. editor, and how it reconciles two earlier semi-decisions in PRD.md/ARCHITECTURE.md) does.

One implementation pitfall worth recording: `mermaid.render(id, code)` throws if an element with `id` already exists in the live document, and it also leaves its own internal scratch container (`#d<id>`, appended directly to `document.body`) behind on both some failure paths and reuse. A component that reuses a fixed id across re-renders, or that conditionally unmounts its own render target while showing an error state, gets stuck permanently — a later successful render has nowhere to write its result, and the error never clears. `MermaidDiagram` generates a fresh id per render attempt, removes mermaid's own scratch container in a `finally` block, and keeps the render target mounted (hidden via CSS, not unmounted) even while showing an error, specifically so a subsequent successful render can still take effect.
