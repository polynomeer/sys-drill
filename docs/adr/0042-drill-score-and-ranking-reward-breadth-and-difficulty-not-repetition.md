# 점수·랭킹을 도입하되, 반복 파밍이 이득이 되지 않는 구조로 만든다

[LEARNING_COMMUNITY_PLAN.md](../LEARNING_COMMUNITY_PLAN.md) §3은 "순위 중심 리더보드"를 **안티골**로 적었다. 이유는 측정 왜곡이었다 — 순위가 걸리면 점수를 올리기 쉬운 시나리오만 반복하게 되고, 그건 이 제품이 기르려는 역량과 정반대 방향이다. 사용자가 그 우려를 확인하고 도입을 결정했다. **이 ADR이 그 안티골을 대체한다.**

**점수(Drill Score)와 티어·백분위를 도입한다. 단, 우려했던 왜곡이 구조적으로 이득이 되지 않도록 설계한다.**

```
DrillScore = Σ  (공식 도메인 d의 최고 세션 점수) × 난이도가중(d)
             d
난이도가중:  EASY 1.0 · MEDIUM 1.2 · HARD 1.5
```

왜곡 방지는 부가 규칙이 아니라 이 수식 자체에서 나온다.

1. **도메인별 최고점만 합산한다.** 같은 시나리오를 100번 풀어도 최고 1회만 반영되므로 반복 자체에 보상이 없다. 이건 새로 만드는 규칙이 아니라 `CertificationService.bestScoreByDomain`이 이미 쓰는 계산을 그대로 재사용한 것이다.
2. **쉬운 것만 반복하는 전략의 상한이 낮다.** EASY 도메인은 현재 하나뿐이라 만점을 받아도 100점이고, 전체 상한(940점)의 약 10%다. 점수를 올리는 유일한 길은 **안 해 본 도메인, 더 어려운 도메인으로 가는 것**이다.
3. **넓이가 자동으로 보상된다.** 도메인에 대한 합이므로 안 푼 도메인은 0점이다. 커버리지 보너스 같은 별도 항을 두지 않아도 넓이가 점수에 직접 들어간다.
4. **공식 시나리오만 집계한다.** 조직 전용·사용자 제작 시나리오는 제외한다. 그러지 않으면 자기가 만든 쉬운 시나리오로 점수를 찍어낼 수 있다. 이 역시 `CertificationService`가 이미 쓰는 필터(`organizationId == null && creatorUserId == null`)다.

**대응 품질은 이 점수에 섞지 않는다.** MTTR·잘못된 액션 수는 별도 보드로 분리한다. 하나의 숫자에 이질적인 축을 임의 가중치로 뭉개면 아무도 그 숫자를 설명할 수 없게 되고, 설명할 수 없는 점수는 신뢰받지 못한다.

**표시 방식**도 왜곡 방지의 일부다. 절대 순위(3등)보다 **티어와 백분위**를 앞세운다. 1등 경쟁은 소수에게만 의미가 있고 나머지에게는 동기를 깎지만, "상위 30%, 대응자 티어"는 모두에게 다음 목표를 준다. 누적 점수만으로는 초기 사용자가 영구히 유리하므로 "최근 30일 상승폭" 보드를 함께 둔다.

**저장하지 않고 읽기 시점에 계산한다** — [0011](0011-derived-values-are-never-persisted.md)을 따르며, 계산 재료(세션·평가)가 이미 전부 DB에 있다. 다만 랭킹은 본질적으로 전체 사용자 스캔이라 세션 수가 늘면 비싸진다. 그때는 0011이 열어 둔 길("명시적으로 캐시하되 입력에 연동해 무효화한다")을 따라 Redis 캐시를 붙이고, 점수를 세션 저장 경로에 끼워 넣지 않는다.

**받아들이는 대가**: 점수가 붙는 순간 사용자는 점수를 최적화한다. 위 장치들은 최적화의 방향을 "더 넓고 더 어려운 훈련"으로 돌려놓을 뿐 최적화 자체를 없애지 못한다. 난이도 가중치와 티어 구간은 설정값으로 두고, 실제 분포를 보고 조정한다. 조정이 필요해진다는 것은 실패가 아니라 예상된 운영이다.
