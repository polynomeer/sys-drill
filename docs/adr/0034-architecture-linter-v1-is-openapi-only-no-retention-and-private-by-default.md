# Architecture Linter v1 accepts only an OpenAPI spec (not a repository), never persists the raw input, and generated scenarios are private to their creator by a new `Scenario.visibility` axis

FUTURE_EXPLORATIONS.md §A's original pitch was full repository import (code/OpenAPI/IaC across languages) with static analysis producing a System Graph. That scope was explicitly why the item stayed a candidate rather than confirmed roadmap: multi-language parsing and customer-source-code egress are both hard problems this MVP shouldn't take on before anyone has confirmed they want it. We picked the narrowest slice that still delivers "generate a scenario from *my* actual system": a single OpenAPI document. One well-audited parser (`io.swagger.parser.v3:swagger-parser`) covers the whole input format, and an API contract is meant to be shared — unlike source code, uploading one carries essentially none of the confidentiality risk the original pitch worried about. The corollary is real: `ArchitectureRiskScanner` can only prove what a single document proves (missing error responses, no security requirement, unbounded list responses, no request validation) — the original vision's multi-service risks (SPOF, contract drift between services) need a real System Graph across multiple sources, which stays out of scope until repository import exists.

The uploaded spec content itself is never written to the database — `ArchitectureAnalysisService.analyze()` parses it, scans it, and discards it within the same request, keeping only the scenario text the scan produced. This mirrors [0011](0011-derived-values-are-never-persisted.md)'s "derived values only" pattern one step further: even the *input* to the derivation doesn't survive past the request that used it, which is what actually neutralizes the "do we retain a customer's API contract" concern — there's nothing to retain.

Generated scenarios default to invisible to everyone but their creator, via a new `Scenario.visibility` column (`"PUBLIC"`, the default every pre-existing row gets; `"PRIVATE"`, set only by this feature) — a third independent axis alongside `organizationId` ([0001](0001-plain-uuid-scalar-references-across-aggregates.md)-era convention) and `creatorUserId` ([0031](0031-marketplace-scenarios-join-the-public-pool-with-no-payment-in-v1.md)). An uploaded spec's endpoint names and paths can reveal internal product structure even though the document itself is "just a contract," so defaulting to public the way marketplace scenarios do would leak that structure to anyone browsing. The visibility check had to be added in three places that previously only checked `organizationId`: the two public listing queries (`GET /scenarios`, `GET /marketplace/scenarios`) and, critically, `SessionService.startSession` — a PRIVATE scenario still has `organizationId == null`, so without an explicit check anyone could have started a session on someone else's generated scenario by guessing or observing its id.
