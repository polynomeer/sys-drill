# 토론은 시나리오 단위 인앱 스레드로 구현하고, GitHub Issues 링크를 대체한다

Community 탭은 지금까지 GitHub Issues로 나가는 링크 한 장이었고, [LEARNING_COMMUNITY_PLAN.md](../LEARNING_COMMUNITY_PLAN.md) §6.5는 인앱 토론을 **보류**하라고 권고했다 — 게시판은 새 테이블·알림·신고·모더레이션을 끌고 오고, 사용자가 적으면 빈 게시판이 오히려 제품을 초라하게 만든다는 이유였다. 사용자가 그 권고를 검토하고 인앱 구현을 선택했으므로, 여기 기록하는 것은 그 결정과 그 대가다.

**시나리오 단위 토론 스레드를 앱 안에 만든다.**

결정적인 이유는 **맥락**이다. 이 제품에서 질문은 "내가 이 시나리오에서 62점을 받았는데 왜 이 설계가 감점인가", "이 인시던트에서 Rate Limit을 먼저 걸어야 하나 Cache TTL을 먼저 건드려야 하나" 같은 형태로 나온다. GitHub Issues에서는 그 맥락 — 내 답안, 받은 지적, 그 시나리오의 지표, 커뮤니티 분포 — 이 전부 끊기고, 질문자가 상황을 글로 다시 설명해야 한다. 토론이 학습 루프의 일부로 작동하려면 루프가 도는 곳에 있어야 한다.

**받아들이는 대가**는 권고가 지적했던 그대로다. 신고 처리와 숨김 같은 모더레이션 책임이 생기고(`PLATFORM_ADMIN`이 맡는다), 알림이 필요해지며, 초기에 스레드가 비어 있을 위험을 떠안는다. 마지막 항목은 시나리오 단위로 범위를 좁혀 완화한다 — 자유 게시판이 아니라 "이 시나리오에 대한 질문"이므로, 스레드가 없으면 빈 게시판이 아니라 그냥 아직 질문이 없는 화면이다.

**범위 제한** — 이 결정이 허용하는 것은 여기까지다.
- 시나리오(정확히는 `scenario_version_id`) 단위 스레드만. 자유 주제 게시판·DM·팔로우는 이 결정에 포함되지 않는다.
- 전송은 **폴링**이다. [0026](0026-game-day-spectating-is-scoped-by-shared-org-membership-and-still-defers-websocket.md)이 관전 채팅에서 WebSocket을 미룬 판단을 그대로 연장한다.
- 스키마와 조회 패턴은 `session_chat_messages`를 참조 구현으로 삼는다.
- 공개 풀이 본문은 [0041](0041-shared-writeups-are-visible-only-to-users-who-completed-that-scenario.md)의 열람 조건을 따르므로, 스레드에서 풀이를 인용할 때도 같은 조건이 걸린다.
