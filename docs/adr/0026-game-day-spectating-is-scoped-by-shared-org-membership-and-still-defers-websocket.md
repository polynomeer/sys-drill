# Game Day spectating is scoped by shared organization membership, not by which org owns the scenario, and still defers WebSocket despite being the feature that was supposed to justify it

A Game Day spectator is anyone who shares *any* organization with a session's owner (`SessionAccessGuard.requireOwnerOrSpectator` diffs the owner's and caller's `OrganizationMembership` rows for an overlap) — not, as first implemented, anyone whose organization owns the session's scenario via `Scenario.organizationId` ([0024](0024-custom-scenarios-coexist-with-migration-content-and-scope-cut-to-design-only.md)). The first version was caught in this step's own browser verification: a custom scenario is capped at INITIAL+FOLLOWUP with no Incident step (that same ADR's scope cut), so a session on an org-owned scenario can *never* reach the Wargame phase spectating exists to watch — scoping by scenario ownership would make Game Day watch nothing in practice. Scoping by shared membership instead means teammates can spectate each other's sessions on any scenario, public ones included — which is also where every real Incident/Wargame phase actually lives today. The corresponding "active team sessions" listing (`GET /organizations/{orgId}/game-day-sessions`) follows the same shape: every organization member's active sessions, not just sessions on that organization's own custom scenarios.

This is still not a dedicated `SessionParticipant`/invite table — it's a live membership check, so anyone who joins or leaves an organization gains or loses spectator access to that org's live sessions immediately, with no per-session invite step. Revisit if Game Day needs anything finer-grained (e.g. spectators from outside the owner's organization, or excluding some members from a given session).

`docs/ARCHITECTURE.md`'s "실시간 UX" section states plainly that "WebSocket은 실시간 멀티플레이 워게임 이전에는 불필요하다" (WebSocket is unnecessary before real-time multiplayer Wargame) — this feature is that moment, and yet it still ships on the existing 3-second polling pattern with no WebSocket, SSE, or pub-sub of any kind, for state, timeline, and the new chat channel alike. The reason the anticipated trigger didn't fire: v1 is spectate-only. A spectator tolerating a few seconds of staleness costs nothing — the actual pressure toward push-based transport is multiple people *simultaneously acting* on shared state (which would need to react instantly to each other, and would also need to fix `SimulationService.applyAction`'s existing last-write-wins race, untouched here because only the owner can act). That is explicitly out of this step's scope; WebSocket adoption should wait for it.
