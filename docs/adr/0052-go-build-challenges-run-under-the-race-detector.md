# Go 과제 채점은 레이스 디텍터 아래에서 돈다

동시성 단계(queue·event-bus·distributed-lock 4단계, rate-limiter 3단계)는 결과값으로 판정한다 — "1000개를 정확히 한 번씩 받았는가", "라운드마다 정확히 한 명만 락을 잡았는가". Java·Kotlin에서는 락 없는 구현이 이 판정에 매번 걸리지만, Go에서는 대부분 통과했다: 샌드박스의 0.5 CPU 쿼터 때문에 Go 1.25가 `GOMAXPROCS`를 2로 잡고, 쿼터 안에서 고루틴이 실제로 겹치는 일이 드물어 check-then-set 사이에 끼어드는 일이 거의 일어나지 않는다. 메시지 수를 1000개로 늘리고 `GOMAXPROCS(8)`을 줘도 락 없는 queue는 3번 중 2번, distributed-lock은 3번 중 0번만 잡혔다.

**결정**: Go 채점 명령을 `go run -race`로 바꾸고, 이미지에 `CGO_ENABLED=1`, `GORACE=halt_on_error=1`, 레이스용 표준 라이브러리 빌드 캐시를 넣는다. 레이스 디텍터는 실제로 겹쳤는지가 아니라 happens-before 관계로 동기화 없는 접근을 잡기 때문에, 같은 락 없는 구현 세 가지가 9번 중 9번 걸렸다(정답은 그대로 통과, 단계당 약 3초). 경쟁이 나면 첫 경쟁에서 프로세스가 멈춰 `RESULT:PASS`를 찍지 못하고, 워커는 스택 꼬리 대신 "data race — …" 피드백을 준다.

**대안과 이유**: 테스트 쪽에서 경쟁 창을 넓히는 방법(rate-limiter처럼 제공 코드에 지연을 넣기)은 학습자가 직접 짜는 저장소(queue·lock store)에는 쓸 수 없다. CPU 한도를 Go만 올리는 쪽은 겹침 확률을 올릴 뿐 결정적이지 않고 호스트 자원을 더 쓴다. 다른 언어에는 같은 도구가 없다 — JVM은 결과값 판정으로도 충분히 잡히고, CPython은 GIL 때문에 락 없는 짧은 check-then-set이 사실상 원자적으로 돌아 어떤 테스트로도 안정적으로 드러나지 않는다(이 한계는 그대로 둔다).

**대가**: Go판은 다른 언어판보다 엄격하다 — 결과가 우연히 맞아도 동기화 없는 접근이 있으면 실패한다(동시성 단계에서는 의도한 바다). 레이스 디텍터 때문에 Go 실행이 단계당 1~2초 느려지고, 이미지에 cgo 툴체인과 레이스 캐시가 들어간다. 레이스 디텍터는 실제로 실행된 경로만 보므로 테스트가 건드리지 않는 경쟁은 여전히 못 잡는다.
