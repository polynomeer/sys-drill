# Learning 개념 콘텐츠는 DB에 두고, 프론트 상수 `riskLabels.ts`는 단일 출처 자리를 내준다

[LEARNING_COMMUNITY_PLAN.md](../LEARNING_COMMUNITY_PLAN.md) §5가 설계한 개념 라이브러리는 `RuleEvaluator`의 riskKey 25개마다 정의·증상·해결 패턴·트레이드오프·관련 도메인/액션/과제를 붙인다. 이 콘텐츠를 어디에 둘지가 문제였다. 지금 이 정보의 조각(한국어 라벨과 한 줄 설명)은 프론트엔드 상수 `frontend/src/lib/riskLabels.ts`에 있고, Learning 화면은 그걸 그대로 렌더링한다.

**콘텐츠는 `learning_concepts` 테이블에 두고 Flyway 시드 마이그레이션으로 배포한다.** 프론트 상수는 제거하고, 라벨을 포함한 모든 필드를 API가 내려준다.

이 저장소는 이미 같은 종류의 결정을 세 번 같은 방향으로 내렸다 — 시나리오 콘텐츠([0002](0002-content-via-migrations-not-admin-crud.md)), Build 채점 스크립트와 프롬프트 템플릿([0006](0006-config-as-data.md))이 전부 파일시스템이나 코드가 아니라 DB에 있고 마이그레이션으로 배포된다. 개념 설명도 같은 범주의 콘텐츠다. 결정적인 이유는 **서버가 이 데이터를 읽어야 한다**는 것이다: 개념 목록에 "내가 3번 놓친 개념" 배지를 붙이려면 riskKey별 집계와 개념 메타데이터를 같은 곳에서 조인해야 하고, 개인 학습 경로(§5.3)는 개념의 `relatedDomains`/`relatedChallenges`를 읽어 다음 훈련을 고른다. 콘텐츠가 프론트에만 있으면 서버는 자기가 추천하는 개념이 무엇인지 모른다.

대안은 현행 유지, 즉 프론트 상수에 설명을 덧붙이고 개인화는 프론트에서 합성하는 것이었다. 초기 비용은 더 싸지만 두 가지를 잃는다. 첫째, 학습 경로 생성 로직이 프론트로 넘어가 `SkillProfileController`가 이미 하고 있는 "약점 → 추천" 계산과 갈라진다. 둘째, 라벨은 프론트에 설명은 DB에 있는 어정쩡한 이중 출처가 생기기 쉽다 — 실제로 지금도 `riskLabels.ts`의 25개 키와 `RuleEvaluator.categoryByRiskKey`의 25개 키가 손으로 동기화되고 있어, 한쪽만 바뀌면 조용히 어긋난다. 이번 이관은 그 이중 관리를 없애는 쪽이기도 하다.

**받아들이는 대가**: 개념 문구를 고치려면 마이그레이션을 추가해야 한다(0002가 이미 받아들인 것과 같은 대가 — 관리자 CRUD 화면은 여전히 없다). 또 프론트가 개념 라벨을 얻으려면 API 호출이 필요해져, 지금처럼 상수를 import해 즉시 렌더링하던 화면 몇 곳이 로딩 상태를 갖게 된다.

**범위 밖**: riskKey → 카테고리 매핑(`RuleEvaluator.categoryByRiskKey`)은 **코드에 남긴다.** 그 매핑은 콘텐츠가 아니라 채점 엔진의 분류 로직이고, 평가 파이프라인이 런타임에 쓰기 때문이다. `learning_concepts.category`는 그 매핑을 복제하는 것이 아니라 시드 시점에 그것으로부터 채워지는 값이며, 둘이 어긋나지 않도록 검증하는 테스트를 함께 둔다.
