# 메커니즘 위젯은 엔진이 아니라 Build 과제 스펙을 근거로 둔다

2차 기획(docs/LEARNING_EXPANSION_PLAN.md §6)은 "Visualize 위젯(Consistent Hashing 등)"을 보류했다 — 규칙 엔진은 도메인 단위의 사용률·지연만 계산하고 토큰 버킷이나 해시 링 같은 메커니즘은 모델링하지 않으므로, 위젯은 채점과 무관한 프론트 전용 시뮬레이터가 되어 Drill·랩과 다른 말을 할 위험이 있었다. 그 뒤 같은 메커니즘들이 Build 과제로 생겼고, 스테이지마다 동작이 5개 언어 테스트로 고정됐다.

**결정**: 메커니즘 위젯(L17)은 엔진 대신 **Build 과제의 스테이지 스펙**을 근거로 둔다. 위젯의 시나리오는 데이터로 두고, 각 시나리오가 어느 스테이지의 어떤 값(용량·윈도·요청 수·기대 결과)을 쓰는지 명시한다. `npm run check:mechanisms`가 (1) 위젯의 시뮬레이션 코어가 그 시나리오에서 기대 결과를 내는지, (2) 그 값들이 실제 Build 스테이지 테스트 파일(Python·TypeScript 판)에 그대로 있는지 대조한다. 위젯은 순수 클라이언트 계산(가상 시계, 결정론적)이고 서버를 부르지 않는다. 위젯마다 "직접 구현해 보기 → Build 과제" 링크를 둔다.

**대안과 이유**: 엔진을 메커니즘 수준으로 확장하는 안은 엔진을 도메인 수식에서 이산 사건 시뮬레이터로 바꾸는 일이라 ADR-0045·0047의 전제를 흔든다. 위젯 수치를 자유롭게 정하는 안은 2차 기획이 보류한 바로 그 위험(별도 진실)이다. Build 스펙은 이미 학습자가 구현하고 채점받는 기준이라, 위젯이 그 스펙과 같은 말을 하면 "보고 → 직접 만들어 같은 테스트를 통과"가 하나로 이어진다. 위젯 코어를 Build의 TypeScript 판 스테이지 테스트로 직접 돌리는 안도 검토했으나, Build 판은 실제 시간과 비원자적 async 저장소를 쓰는 반면 위젯은 가상 시계로 장면을 재생해야 해 인터페이스가 맞지 않았다 — 값 대조로 대신한다.

**대가**: 값 대조는 테스트 파일의 문자열(`RateLimiter(capacity=3, window_seconds=10.0)` 등)을 찾는 방식이라, Build 테스트를 리팩터링하면(값은 같아도 표기가 바뀌면) 검사도 함께 고쳐야 한다. 위젯이 보여 주는 비교 알고리즘(토큰 버킷 등)처럼 Build 스테이지가 직접 고정하지 않는 부분은 위젯 코어의 자체 기대값으로만 지킨다.
