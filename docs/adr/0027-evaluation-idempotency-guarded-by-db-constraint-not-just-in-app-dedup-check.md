# Evaluation idempotency is guarded by a DB unique constraint, not just `EvaluationWorker`'s in-transaction dedup check

`EvaluationWorker.processJob` already checked `existsBySubmissionIdAndIsActiveTrue` before evaluating a submission, to make redelivery of the same Redis job a no-op. That check and the later `Evaluation` insert are two separate statements in the same transaction, not one atomic operation — a redelivered (or, once this runs as more than one instance per docs/ARCHITECTURE.md §2, cross-instance) duplicate of the same job can run its own transaction, see zero active evaluations before either side commits, and insert anyway. The result was two active `Evaluation` rows for one submission, discovered via `EvaluationWorkerIntegrationTest`'s "duplicate delivery of the same job is processed at most once" — flaky specifically because triggering the race needed a second concurrent deliverer, and in practice that second deliverer was a leftover local `bootRun` process sharing the dev Postgres/Redis containers with the test run, not something the test controlled deterministically.

The fix is `V28__unique_active_evaluation_per_submission.sql`, a partial unique index (`unique index ... on evaluations (submission_id) where is_active`), plus catching the resulting `DataIntegrityViolationException` in `EvaluationWorker` as an expected "another delivery already won" outcome rather than a real failure. The alternative was a Redis-side dedup (e.g. `SETNX` a per-submission processing key before dequeuing), which would avoid touching the schema but only protects against redelivery through this same queue — it does nothing if a second consumer ever writes an `Evaluation` some other way, and it adds a second source of truth (a Redis key with its own TTL/cleanup) for a fact the database can already enforce for free. The DB constraint makes "at most one active evaluation per submission" true no matter how a duplicate write is triggered, which is the actual invariant the pipeline needs.

This changes the transaction's error handling: a `DataIntegrityViolationException` from the insert must not fall into the same catch as a real evaluation failure (`handleFailure`, which re-enqueues for retry) — Postgres has already aborted that transaction, so any further JDBC call inside it (including `handleFailure`'s own status update on final-attempt failure) would itself fail. It's now caught separately and rethrown to unwind the transaction cleanly, then logged as an info-level "lost the race" outcome at the `processJob` level.
